# ADR-0050: A server is known by its key, never by its address

**Status**: accepted. **Amends [ADR-0040](0040-a-server-agent-links-to-its-control-plane.md)** (what the handshake pins, which link wins, the host running Deplo), **[ADR-0006](0006-server-agent-is-a-per-host-go-binary.md)** decision 4 (the pin) and **[ADR-0011](0011-server-removal-is-trust-revocation-not-a-host-uninstall.md)** (what removal revokes).

ADR-0040 made every server agent dial out and keep one link, trusted by a pinned certificate fingerprint. But "one machine" still meant "one address". Adding a server took a typed address, enrollment refused a second server at an address already used, and the host running Deplo was the server whose address matched the machine's own. Two real setups broke. Deplo behind NAT did not recognise its own host, so its agent linked through the public address and lost the loopback path. Several virtual machines behind one public address, the ordinary Proxmox setup, could not all be added. Addresses change, and a copy of a machine behind the same router has the same one, so an address can never be an identity.

## Decision

1. **The identity of a server is its agent's key pair.** The control plane pins the agent's public key, the sha256 of its certificate's public key. The pin is read from the stored certificate, so every existing pin carries over with no migration step and no reinstall. The certificate is paper. Deplo's CA signs it, and its dates are the renewal schedule, not a reason to refuse. A link whose pinned certificate has passed its date is accepted when the CA signed it and its key is the pinned one, and Deplo rotates the key at once. Every other link gets the full chain and date check, with the pinned key on top.

2. **The key rotates over the authenticated link every 30 days.** The agent makes a new key, and the private half never leaves the machine. It sends a signing request, and Deplo signs it and stores the new certificate as the server's next one before the agent installs it. A link presenting the next certificate is accepted and promotes it, so a rotation cut halfway never locks a server out. Once promoted, the old key is retired. The link the rotation ran over stays open, so no deploy, backup or console on it is cut; the next link proves the new key. A machine that proves it holds a retired key, by completing the handshake with it, is refused and flagged: it is a copy that missed a rotation. The 365-day lifetime stays, so a cluster keeps working that long while Deplo is down, because its members still check each other's dates (ADR-0043).

3. **One identity, one live link.** When a link arrives for a server that already has one, Deplo asks the open link for a Hello. If it answers within 3 seconds, the new link is refused (close code 4003), an alert fires: "Two machines are using the identity of <server>", and the server that kept its link gets a new key at once, at most once an hour. Without that the copy would take the identity over the moment the original went quiet; with it, the copy holds a retired key and is refused for good. The usual cause is a virtual machine cloned with the agent inside, and the fix is a fresh agent on the copy. If the open link does not answer, it was dead, and the new link replaces it as before. A refused agent writes a marker on its own disk, so the installer later knows that machine is a copy and gives it its own identity without asking.

4. **The address is never typed, and nothing is unique by address.** Adding a server asks for a name only. Deplo records where each link and each enrollment comes from and shows it as **Connected from**. Behind the panel's proxy it takes the visitor address only from the hop that proxy appended (`clientAddress`), and through the panel's Cloudflare Tunnel from the hop Cloudflare appended ([ADR-0042](0042-the-panel-can-be-served-through-a-cloudflare-tunnel.md)). A connection that did not come through either, such as the host's own loopback link, is its socket's address. Two servers may share a public address.

5. **The host running Deplo is the server the installer enrolled for this machine.** It is marked once, from the installer's own bootstrap token, and never found again by comparing addresses. An existing install is marked by that token, or once by the old address match when the token is gone. A second install on a machine that already has an agent is stopped by the installer on the machine itself, unless it reinstalls the same server or the machine is a known copy.

6. **An App's address is a separate fact from "Connected from".** It is the agent's own reported addresses, editable under Advanced as before. When a server connects from an address that is not one of its own, it is behind a router, and its screen says that its Apps answer on that address only if the router forwards ports 80 and 443 to it. A cluster never names one public address for two members, in its zone's answers, its glue or its name servers. The member that joined first keeps it, and the cluster's screen says why.

7. **A cluster member's key rotates only once its cluster holds the next one.** Members pin each other's certificates ([ADR-0044](0044-cluster-members-meet-through-a-relay-over-tcp.md)), so a rotation changes what every other server of the cluster must accept. Before a member installs its next key, Deplo hands the next certificate to every server of each of its clusters, to every relay and to the leader that leads it. When one cannot take it, because it is off or its agent or leader is too old, the key is not installed and the rotation waits for the next check, 12 hours later. A table that names a server by its old certificate accepts the new one, never the other way round. So a server that was off when the rotation was promoted still reaches the member while Deplo is down: its private network, replication, its names and its zone's answers keep working. A copy holding the retired key gains nothing from it: Deplo refuses it and flags it as before, the relays drop the old key at the promotion, and every table that names the new key refuses the old one. A certificate within 30 days of its date rotates anyway, because past its date every member would refuse it.

## How comparable systems do it

| System                    | Identity                                     | Expiry                                               | Off past its date                         | A copy                                       |
| ------------------------- | -------------------------------------------- | ---------------------------------------------------- | ----------------------------------------- | -------------------------------------------- |
| WireGuard                 | Static public key                            | None                                                 | Works                                     | Undetected; both peers fight over one key    |
| SSH host keys             | Host key, trusted on first use or by a CA    | None for keys; a CA certificate's validity if signed | Works with keys; a signed one needs a new | Undetected                                   |
| Tailscale                 | Machine key, plus a node key                 | Node key every 180 days, off for tagged servers      | A person logs in again                    | Not what expiry is for                       |
| kubelet                   | Client certificate                           | Rotated at 70-90% of its lifetime                    | Needs the bootstrap token again           | Undetected                                   |
| SPIFFE / SPIRE            | Short-lived SVID after node attestation      | Hours, rotated at half-life                          | Re-attests; a join token works only once  | Attestation (TPM, cloud) tells them apart    |
| **Deplo (this decision)** | **Pinned public key, CA-signed certificate** | **Key rotated every 30 days over the link**          | **Accepted by key, rotated at once**      | **Refused while the first answers, flagged** |

What Deplo takes from each: the key as the identity (WireGuard, SSH), rotation over the authenticated channel before the date (kubelet, Tailscale's seamless renewal), and a separate long-lived key next to the rotating one (Tailscale's machine key). The pinned key of a rotation plays that part here. What it does not take: forcing a person to act when a date passes (Tailscale, kubelet without its token), because a server that was off for a month is not suspect. Hardware attestation (SPIRE's TPM) is the only thing that truly tells a copy from its original, and most servers Deplo runs on have none. So Deplo detects a copy by behaviour instead: two live links at once, or a key that missed a rotation.

## Considered options

- **Pin the certificate and reissue it before its date**: rejected. A server that is off across the date can only come back with a reinstall, which the mission forbids.
- **A manual approval in the panel as the defence against copies**: rejected as the main defence. Addresses change and a copy behind the same router has the same one, so the person approving has nothing to judge by. Recovery stays the server's own reinstall command, which a person runs only when both machines are theirs to sort out.
- **Drop certificate dates altogether**: rejected. Cluster members still check them between each other while Deplo is down, and the dates give rotation a schedule a person can read.
- **Rotate the key at every link**: rejected. A copy and its original would take turns rotating each other out, and every rotation pushes rosters to every cluster relay.
- **Keep refusing a second server at a used address**: rejected. It is what broke the two setups above, and it never stopped a copy, which has its own address only by luck.
- **Rotate a cluster member at once and let the others hear of it from Deplo**: rejected. A server off at that moment and back while Deplo is down cannot reach the member: the relay knows only the new key, and every stream to the member is pinned to the old one. Proven by `TestRotation_aMemberBackWhileDeploIsDownReachesTheMemberThatRotated` in `deplo-agent`.
- **Members trust any certificate the CA signed for the same server**: rejected. A copy holding the retired key would keep its place in the cluster, and a member behind the relay alone cannot find the new name anyway.
- **Trust `x-forwarded-for` from any connection**: rejected. The link door is also reached on the host's loopback, where anyone on the machine can send that header.
