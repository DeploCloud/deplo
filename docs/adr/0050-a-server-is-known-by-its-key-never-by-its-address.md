# ADR-0050: A server is known by its key, never by its address

**Status**: accepted; decisions 8 to 11 added on 22 Nov 2026 (agent DeploCloud/deplo-agent#83, panel #294, migration 0275); decisions 12 to 17 added the same day (agent DeploCloud/deplo-agent#85); decision 18 added the same day. **Amends [ADR-0040](0040-a-server-agent-links-to-its-control-plane.md)** (what the handshake pins, which link wins, the host running Deplo), **[ADR-0006](0006-server-agent-is-a-per-host-go-binary.md)** decision 4 (the pin) and **[ADR-0011](0011-server-removal-is-trust-revocation-not-a-host-uninstall.md)** (what removal revokes).

ADR-0040 made every server agent dial out and keep one link, trusted by a pinned certificate fingerprint. But "one machine" still meant "one address". Adding a server took a typed address, enrollment refused a second server at an address already used, and the host running Deplo was the server whose address matched the machine's own. Two real setups broke. Deplo behind NAT did not recognise its own host, so its agent linked through the public address and lost the loopback path. Several virtual machines behind one public address, the ordinary Proxmox setup, could not all be added. Addresses change, and a copy of a machine behind the same router has the same one, so an address can never be an identity.

## Decision

1. **The identity of a server is its agent's key pair.** The control plane pins the agent's public key, the sha256 of its certificate's public key. The pin is read from the stored certificate, so every existing pin carries over with no migration step and no reinstall. The certificate is paper. Deplo's CA signs it, and its dates are the renewal schedule, not a reason to refuse. A link whose pinned certificate has passed its date is accepted when the CA signed it and its key is the pinned one, and Deplo rotates the key at once. Every other link gets the full chain and date check, with the pinned key on top.

2. **The key rotates over the authenticated link every 30 days.** The agent makes a new key, and the private half never leaves the machine. It sends a signing request, and Deplo signs it and stores the new certificate as the server's next one before the agent installs it. A link presenting the next certificate is accepted and promotes it, so a rotation cut halfway never locks a server out. Once promoted, the old key is retired. The link the rotation ran over stays open, so no deploy, backup or console on it is cut; the next link proves the new key. A machine that proves it holds a retired key, by completing the handshake with it, is refused and flagged: it is a copy that missed a rotation. The 365-day lifetime stays, so a cluster keeps working that long while Deplo is down, because its members still check each other's dates (ADR-0043).

3. **One identity, one live link.** When a link arrives for a server that already has one, Deplo asks the open link for a Hello. If it answers within 3 seconds, the new link is refused (close code 4003), an alert fires: "Two machines are using the identity of <server>", and the server that kept its link gets a new key at once, at most every 10 minutes. Without that the copy would take the identity over the moment the original went quiet; with it, the copy holds a retired key and is refused for good. The usual cause is a virtual machine cloned with the agent inside, and the fix is a fresh agent on the copy. If the open link does not answer, it was dead, and the new link replaces it as before. A refused agent writes a marker on its own disk, so the installer later knows that machine is a copy and gives it its own identity without asking.

4. **The address is never typed, and nothing is unique by address.** Adding a server asks for a name only. Deplo records where each link and each enrollment comes from and shows it as **Connected from**. Behind the panel's proxy it takes the visitor address only from the hop that proxy appended (`clientAddress`), and through the panel's Cloudflare Tunnel from the hop Cloudflare appended ([ADR-0042](0042-the-panel-can-be-served-through-a-cloudflare-tunnel.md)). A connection that did not come through either, such as the host's own loopback link, is its socket's address. Two servers may share a public address.

5. **The host running Deplo is the server the installer enrolled for this machine.** It is marked once, from the installer's own bootstrap token, and never found again by comparing addresses. An existing install is marked by that token, or once by the old address match when the token is gone. A second install on a machine that already has an agent is stopped by the installer on the machine itself, unless it reinstalls the same server or the machine is a known copy.

6. **An App's address is a separate fact from "Connected from".** It is the addresses Deplo proved reach the server (decisions 8 to 11), no longer typed under Advanced. When a server connects from an address that is not one of its own, it is behind a router, and its screen says that its Apps answer on that address only if the router forwards ports 80 and 443 to it. A cluster never names one public address for two members, in its zone's answers, its glue or its name servers. The member that joined first keeps it, and the cluster's screen says why.

7. **A cluster member's key rotates only once its cluster holds the next one.** Members pin each other's certificates ([ADR-0044](0044-cluster-members-meet-through-a-relay-over-tcp.md)), so a rotation changes what every other server of the cluster must accept. Before a member installs its next key, Deplo hands the next certificate to every server of each of its clusters, to every relay and to the leader that leads it. When one cannot take it, because it is off or its agent or leader is too old, the key is not installed and the rotation waits for the next check, 12 hours later. A table that names a server by its old certificate accepts the new one, never the other way round. So a server that was off when the rotation was promoted still reaches the member while Deplo is down: its private network, replication, its names and its zone's answers keep working. A copy holding the retired key gains nothing from it: Deplo refuses it and flags it as before, the relays drop the old key at the promotion, and every table that names the new key refuses the old one. A certificate within 30 days of its date rotates anyway, because past its date every member would refuse it. So does the key of a server whose copy was caught (decision 18).

## Its addresses are found and proven, never typed (22 Nov 2026)

The owner's cluster `eu` showed decision 6's "editable under Advanced" go wrong both ways. eu-1 was added at its router's public IPv4, whose 443 reaches another machine and whose 80 is closed, and the cluster's zone published it as an A record and as ns1's glue. eu-2 and eu-3 kept the IPv6 they were installed at, so a new prefix from the ISP would leave a dead address in every answer. So, decided by the owner:

8. **Nobody types a server's address** (decision A). The Advanced form, the `updateServerAddress` mutation, the `address` input of the `update_server` tool and `addServer.host` for an ordinary server are gone; only a migration source, the other platform's machine, still takes one. Deplo finds each server's public addresses itself: those on its own interfaces (Hello `publicAddresses`), and per family the address its traffic leaves from, which the agent asks of Deplo's `/api/address` once over IPv4 and once over IPv6 (`ProveAddresses`, Hello `address.prove`), with the link's own origin beside them.
9. **An address is used only once Deplo proved it reaches that server**, everywhere Deplo publishes or shows one: generated names, a cluster zone's A, AAAA and glue, and every record the screens show. The proof is something only that server can present. On 443: the certificate the server's proxy presents for a name no route has, which its agent reads on its own machine and Deplo compares with what answers at the address; a mismatch that matches another server says which one. On 53, for a name server of a cluster zone: the TXT of `_deplo-server.<zone>`, the server's certificate hashed, which its name server answers even while it answers SERVFAIL for the zone. Deplo checks every 2 minutes from where it runs, never through the server.
10. **An address leaves only after failing for 30 minutes without a break**, about fifteen checks in a row, so a flapping check renames nothing; the server page counts the 30 minutes down and says why in one line ("130.78.60.1 does not reach eu-1: the router sends port 443 elsewhere"). One the machine no longer has, or no longer sends from, leaves at the first failed check: the machine itself says it is gone, as after a new prefix. Deplo never drops an address only because it cannot reach that family itself: it is shown as not checked and keeps the place it had. The upgrade cuts no working server: an address typed before stays in use until its first check.
11. **One choice is left per server, the family** (decision B): Automatic (the default, every proven address; generated names on IPv4 when one is proven, IPv6 otherwise), IPv6 only, or IPv4 only. It replaces "Generated addresses" and reuses its column. Generated names, the zone's records and glue, and the domain hints follow it, and the control says before it applies that the generated names move. When what Deplo uses changes, the server's row takes the new address, its generated names move with it, and its clusters' zone and relay doors follow at once.

## A server belongs to one Deplo (22 Nov 2026)

The owner's cluster `eu` runs on machines that served the lab's Deplo first. Their agents joined the new Deplo and kept everything the lab had written: the lab's cluster in the shared files, one network key known to both clusters' servers, the lab's leader and relay still running on eu-1, the lab's panel as a network peer, and a proxy whose `letsencrypt` resolver ordered from the lab's test authority. Any machine that ran another Deplo before ends up the same way. So, decided by the owner:

12. **An agent belongs to the Deplo whose CA signed its certificate.** It keeps the sha256 of that CA's public key on its disk (`panel`); a reinstall on the same Deplo has the same key and keeps its state. When the agent joins a Deplo, on a fresh install, a reinstall or the installer run over an existing agent, nothing another Deplo left is used again: its cluster files, the network key and peers, its leader and relay, the name server's zones, the name forwarders, the link settings, and in the proxy the resolvers' authority and their root.
13. **Set aside, never deleted.** What another Deplo wrote moves to one dated folder, `set-aside/<UTC time>` in the agent's directory, which nothing loads. Its leader, relay, name server and name forwarders are stopped and removed. The server page says it once, in one line: "Set aside what another Deplo left on this machine", for a week, or for as long as that Deplo's Apps remain.
14. **Another Deplo's App containers and data are never touched.** They are listed in the folder and on the server page for the owner to decide, and a cleanup counts them as live, so their files, images and networks stay.
15. **The agent judges on start, before it loads anything**, so a leftover can never come back. A stamp naming another Deplo sets everything aside. An agent from before the stamp cannot tell its Deplo's clusters from another's, so its Deplo claims it on every link (`ClaimServer`, Hello `panel.claim`): the clusters it has, and whether it runs a leader or relay there. Anything else is noted, and the agent restarts to set it aside before loading; a network key the other Deplo's servers know is replaced, and Deplo hands the new one to the cluster. After the stamp, the claim judges nothing.
16. **The proxy's certificate authority comes from Deplo over the link, never from its file.** On every link Deplo points every resolver at Let's Encrypt, takes out any other authority's server, a test duration, its root and the host name it was reached by. A test authority such as Pebble is accepted only when Deplo itself runs in its certificate test mode (`DEPLO_TEST_ACME_DIRECTORY`, and `DEPLO_TEST_ACME_CA` for its root, written into the proxy by Deplo). When the proxy starts, the agent sets aside an account registered with another authority and, for Let's Encrypt, every certificate that does not chain to a public root.
17. **The upgrade cleans a machine by itself.** The released agent and panel do all of it; nobody edits a server by hand.

Rejected: deleting the other Deplo's state (a mistake on a machine that is the owner's would lose what a backup could not bring back); setting aside everything whenever a stamp is missing (it would take its own Deplo's network and zone from every server on the upgrade, and the zone answers the owner's names); judging every claim, also after the stamp (a cluster created while the claim is on its way would be set aside).

## A caught copy rotates the original at once (22 Nov 2026)

Decision 7 held a caught copy's rotation back like any other: while a member of the cluster was off, the original kept its key and the copy kept being refused only because the original answered. Had the original then gone quiet, the copy would have linked as that server. Decided by the owner:

18. **A copy caught with both machines linked rotates the original at once, even while a server of its cluster is off** (`rotateAfterCopy`, `renewAgentCertIfDue` with `now`): the next key is still handed to every server, relay and leader that can take it first, and is installed whoever could not. Security wins over decision 7's guarantee: a member that was off and comes back while Deplo is down does not reach the rotated server over the private network until Deplo is back and hands it the new key; with Deplo up it is handed the key by the network's next pass, at most 2 minutes after it links. The copy holds the retired key from that moment, so it is refused and flagged for good, whichever machine is on.

## What cluster eu showed (22 Nov 2026, panel v0.8.2-canary.69, agent v0.5.3-canary.32)

- **A clone with the original on**: LXC 104 (eu-1) cloned to a new container with its own MAC and LAN IPv4, started with eu-1 on. Refused as both answered (21:52:58), the alert "Two machines are using the identity of eu-1", eu-1's key rotated at once (21:53:03) and eu-1 never went offline; from then on the clone was refused for holding a retired key, also while eu-1 was frozen for 20 s. The installer on the clone said "This machine is a copy of another server" and gave it its own identity without `--force` (once the clone had the disk room the preflight asks for). Removed from Deplo, container destroyed.
- **Decision 18, with eu-3 off before the clone starts**: a second clone of eu-1. eu-3 could not take the next key, and eu-1 rotated anyway (22:03:17); the clone was refused after. eu-3, started again, heard eu-1 under its new key within 20 s of its start. A second copy within 10 minutes of the first rotates nothing (decision 3); this run waited for it.
- **Found and fixed** (panel #300, not released yet): after a rotation the other name servers heard the server under its new certificate at once but named it by the old one until the zone's next pass, so it left their answers for 45 s (21:53:03 to 21:53:48). Deplo now hands every member the zone right after the promotion.
- **Found, not fixed**: a copy keeps the original's private network key ([ADR-0047](0047-a-cluster-shares-a-private-network-over-wireguard.md)), which no rotation of the certificate replaces. While a clone ran, eu-2 and eu-3 kept naming eu-1 through the 20 s it was frozen; eu-1, its tunnels taken over, heard too few servers and answered SERVFAIL (21:54:40 to 21:55:07); with eu-3 off as well, eu-1 and eu-2 both answered SERVFAIL for 5 s (22:03:45 to 22:03:49), the whole zone. A caught copy needs the original's network key replaced over its own link, and the others handed the new one.

## A caught copy gets a new network key too (23 Nov 2026)

19. **When a copy is caught, the original's private network key is replaced together with its identity.** After the rotation of decision 18, Deplo asks the original's agent to replace the key it names (`SetClusterNetworkRequest.retire_public_key`, Hello `network.rekey`) and hands every other server of its clusters the new public key in the same pass. A key it no longer holds is never replaced twice. The others' tables name only the new key, so the copy, which still holds the old one, is heard by none of them and can never be heard as the original. Between the new key and the others learning it, a few seconds, the original is not heard over the private network; that is under the removal time, so no name server drops it.

## How comparable systems do it

| System                    | Identity                                     | Expiry                                               | Off past its date                         | A copy                                       |
| ------------------------- | -------------------------------------------- | ---------------------------------------------------- | ----------------------------------------- | -------------------------------------------- |
| WireGuard                 | Static public key                            | None                                                 | Works                                     | Undetected; both peers fight over one key    |
| SSH host keys             | Host key, trusted on first use or by a CA    | None for keys; a CA certificate's validity if signed | Works with keys; a signed one needs a new | Undetected                                   |
| Tailscale                 | Machine key, plus a node key                 | Node key every 180 days, off for tagged servers      | A person logs in again                    | Not what expiry is for                       |
| kubelet                   | Client certificate                           | Rotated at 70-90% of its lifetime                    | Needs the bootstrap token again           | Undetected                                   |
| SPIFFE / SPIRE            | Short-lived SVID after node attestation      | Hours, rotated at half-life                          | Re-attests; a join token works only once  | Attestation (TPM, cloud) tells them apart    |
| **Deplo (this decision)** | **Pinned public key, CA-signed certificate** | **Key rotated every 30 days over the link**          | **Accepted by key, rotated at once**      | **Refused while the first answers, flagged** |

What Deplo takes from each: the key as the identity (WireGuard, SSH), rotation over the authenticated channel before the date (kubelet, Tailscale's seamless renewal), and a separate long-lived key next to the rotating one (Tailscale's machine key). The pinned key of a rotation plays that part here. What it does not take: forcing a person to act when a date passes (Tailscale, kubelet without its token), because a server that was off for a month is not suspect. Hardware attestation (SPIRE's TPM) is the only thing that truly tells a copy from its original, and most servers Deplo runs on have none. So Deplo detects a copy by behaviour instead: two live links at once, or a key that missed a rotation.

## Considered options

- **Pin the certificate and reissue it before its date**: rejected. A server that is off across the date can only come back with a reinstall, which the mission forbids.
- **A manual approval in the panel as the defence against copies**: rejected as the main defence. Addresses change and a copy behind the same router has the same one, so the person approving has nothing to judge by. Recovery stays the server's own reinstall command, which a person runs only when both machines are theirs to sort out.
- **Drop certificate dates altogether**: rejected. Cluster members still check them between each other while Deplo is down, and the dates give rotation a schedule a person can read.
- **Rotate the key at every link**: rejected. A copy and its original would take turns rotating each other out, and every rotation pushes rosters to every cluster relay.
- **Keep refusing a second server at a used address**: rejected. It is what broke the two setups above, and it never stopped a copy, which has its own address only by luck.
- **Rotate a cluster member at once and let the others hear of it from Deplo**: rejected. A server off at that moment and back while Deplo is down cannot reach the member: the relay knows only the new key, and every stream to the member is pinned to the old one. Proven by `TestRotation_aMemberBackWhileDeploIsDownReachesTheMemberThatRotated` in `deplo-agent`.
- **Members trust any certificate the CA signed for the same server**: rejected. A copy holding the retired key would keep its place in the cluster, and a member behind the relay alone cannot find the new name anyway.
- **Trust `x-forwarded-for` from any connection**: rejected. The link door is also reached on the host's loopback, where anyone on the machine can send that header.
