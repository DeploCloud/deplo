all three checked on the lab (below). **Before a stable release, four changes and two lab fixes** (below): agent DeploCloud/deplo-agent#73 (Hello `deploy.probe`, v0.5.3-canary.24) and #74 (v0.5.3-canary.25), leader DeploCloud/deplo-cluster#9 (v0.1.0-canary.8), panel #283, #284, #285, #286 (v0.8.2-canary.56 to .59, .60 with the agent pin), manual DeploCloud/docs#18 to #22; checked on the lab. **Under a domain connected to Deplo** (the owner's six decisions of 22 Nov 2026, below): the zone is made and kept in Cloudflare by Deplo, and a name is answered with its App's server first; agent Hello `dns.home`, migration 0274. Follows from [ADR-0048](0048-a-cluster-domain-answers-on-every-server.md), whose third DNS backend (`native`) it is, and which now has two backends, not three.

A domain that answers on every server (ADR-0048) needs one DNS record per healthy server. With a connected provider Deplo keeps them; without one, a person types them and edits them again on every change of the cluster, which is exactly the DNS work the mission keeps off the happy path. **The servers of a cluster answer for a DNS zone themselves: the person delegates a zone (or points one name into it) once, and from then on the cluster's own answers name its healthy servers, with no record to edit, Deplo up or down.**

## Decision

### Where the name server runs: beside every server agent, with none of its privileges

- **Every server of the cluster answers, not the leader.** The leader is one process on one server (or Deplo's machine); a name server there is a single point of failure the moment it matters, a server stopping. The server agent already runs on every server, keeps the cluster's private network on disk and running without Deplo (ADR-0047), and is the only thing allowed to touch the host (ADR-0006), so it is what starts and supervises the name server.
- **The name server is a separate process with nothing of the agent's** (amendment 1). The agent runs as root, holds the Docker socket and its mTLS key, and the name server parses packets from anyone on the internet, so a bug in that parser must reach none of them. The agent binds port 53 itself and starts `deplo-agent dns` (the same binary, like the screenshot browser and the name forwarders) as `nobody` (uid and gid 65534, no supplementary groups, so no `docker` group), chrooted into an empty directory, in a network namespace of its own: it cannot open a single connection, only answer on the sockets it was handed. It never sees the Docker socket, the agent's directory or its keys, and holds no capability. What it receives, over a pipe on its standard input, is the **answer table** and nothing else: the zones and the names in them, the name servers' addresses, and for each cluster the servers to answer with, or "answer with an error". The agent decides health and the majority; the process only answers. If it exits, the agent starts it again on the same sockets, so queries wait in the socket's queue rather than meet a closed port.
- **Port 53, UDP and TCP, on the server's own addresses, never the wildcard**: every address of its network interfaces but loopback, link-local and Docker's, private ones included, since a server behind NAT receives its public address's traffic on its private one. `127.0.0.53` belongs to the host's own resolver on most distributions and `10.201.0.1` to Deplo's DNS cache, and binding the wildcard would collide with both. A server whose port 53 is taken (another DNS server) says so in `SetClusterZone`'s reply, address by address, and Deplo names it as a name server nowhere: the zone works from the others, and the cluster's DNS settings say why.
- **Authoritative only, and small**: no recursion, `REFUSED` outside the delegated zones, no zone transfers, no `ANY` (answered with the one `HINFO` of RFC 8482). Response rate limiting per client network (a /24 for IPv4, a /56 for IPv6; past the limit every second answer is a truncated one, so a real resolver retries over TCP, and the rest are dropped), a cap on TCP connections and on how long each may sit idle. A UDP answer never exceeds what the resolver offers, nor 1,232 bytes: past that it is sent truncated and the resolver asks again over TCP. So the servers are no amplifier. Library: `github.com/miekg/dns` (BSD-3-Clause), the one every Go DNS server uses.

### What it answers, and how it knows who is healthy

- **Deplo hands each agent the zone** (`SetClusterZone`, gated on Hello `dns.zone`): the zones and names delegated, every member's certificate and public addresses, which members are being emptied, the name servers, and the two times. The agent keeps it on disk like the network table, so it answers after a restart with Deplo down.
- **Health is the agent's own view, not Deplo's** (ADR-0048's lab: a stopped server left in the answers also fails certificate checks that land on it): a server is in the answer when this agent heard it over the private network within the removal time (10 s by default; every agent says it is alive every 2 s, so that is five missed), or it is this server, and Deplo has not marked it as being emptied. Each name server answers from what it sees, so the answers outlive Deplo and the leader; the leader's lease state is not needed and not read.
- **Each answer is every healthy server's A and AAAA** for a name of a domain that answers on every server; the NS and SOA of the zone, and the name servers' own addresses; nothing else in phase 1 (no MX, no TXT the person writes: a zone that needs those is delegated one level down, see below). Answers are shuffled per query.

### When a server cannot see enough of its cluster

A name server counts the members of its cluster it hears, itself included, against all of them, servers being emptied included (they are members; they only leave the answer):

- **More than half: it answers** with the healthy servers, and keeps that set on disk as the **last agreed set**.
- **Fewer than half: it answers `SERVFAIL`** for every name of the zone, so resolvers ask another name server, which in a split is one on the bigger side. It never answers "only myself": a server cut off from the server that runs the App cannot pass a visitor on (ADR-0048), so naming itself would send visitors into a 30 s wait. A server cannot tell being cut off from the others having stopped, so this holds when more than half of the servers stop at once too: the zone then waits for them, or for an admin to remove the stopped ones from the cluster, which gives the smaller cluster a majority again.
- **Exactly half, where no side can hold a majority** (an even split of an even cluster, or half of it stopped at once): every server answers **the last agreed set**, stale rather than empty. Two halves each answering it point visitors at servers some of which still carry the App, which is the best a split allows; an empty answer would take every domain down.
- **Just started**: until the agent has listened for one removal time, a server it has not heard yet may simply not have spoken, so it answers the last agreed set (or `SERVFAIL` when it has none) rather than count it as stopped.
- This mirrors the leader's quorum rule (`cluster-rollout.md` §5) without depending on it: DNS never needs a leader to answer.

### The delegation, the only thing typed at the registrar

- **Two shapes, both one step**: delegate a whole zone the person owns only for the cluster (`example-apps.com`), or a subdomain of their main one (`go.example.com`). A name inside the zone needs nothing more. A name outside it gets one `CNAME` into it, named after the domain so no two domains share one: `shop.example.com CNAME shop-example-com.go.example.com`.
- **A `CNAME` cannot carry the bare apex of a domain** (amendment 4): DNS forbids a `CNAME` beside the apex's own `NS` and `SOA`. The screen says so for an apex, and the manual gives the two ways out: make that domain the zone delegated to the cluster, or use an `ALIAS`/`ANAME` record at a DNS provider that offers one, pointed at the same name.
- **Name servers are named inside the zone**, `ns1` to `ns4.<zone>`, so the registrar needs **glue**: an `NS` record and an `A` (and `AAAA`) per name server. Deplo picks at most **four** servers of the cluster, those that answer on port 53 and joined longest ago (in different regions when phase 2 knows them), and keeps the choice stable: it changes the list only when a chosen server leaves the cluster or stops being able to answer, and the zone then says which records to change at the registrar. Four because registrars commonly cap the list there and more adds nothing a resolver uses.
- **The screen shows the exact records with copy buttons and checks them itself**: it asks the parent zone's name servers for the delegation and the glue, and each name server of the cluster for the zone, and says "delegated" or what is missing. It never says "NS" or "glue" before the person opens the details; the first line is "Add these records where you bought the domain."
- **A zone belongs to the cluster, so an instance admin delegates it**, in the cluster's settings, as for everything else about a cluster. Any team with Apps on the cluster then points its domains at it from the domain screen with `manage_domains`, and the zone answers only the names of those domains.

### Geography (phase 2)

- **Each server has a location**: a city an instance admin picks from the release's city list, or a latitude and longitude typed under Advanced, in the cluster's settings (**Server locations**). Until an admin sets one, Deplo places the server where the location table places its first public address, and the screen says "from its address" (owner's decision 1; this replaces "looked up once": derived and live, so a newer table corrects it). A server no table places and no admin placed has no location, and then the zone answers every healthy server to everyone: ranking a server without a place would be a guess.
- **A visitor is placed by EDNS Client Subnet when the resolver sends one, else by the resolver's own address** (amendment 2). A subnet the table has no place for is answered with every healthy server, for that subnet only: the resolver's address is not tried, since the resolver said who it asks for. A `/0` subnet is a client that asked not to be placed, so it counts as no subnet. The answer carries the subnet back (RFC 7871) with a scope of the subnet's own length when the answer depends on it, and 0 otherwise (NS, SOA, a zone with no locations). A malformed subnet (a family other than IPv4 or IPv6, a prefix longer than the family, address bits past the prefix, two subnets in one query) is answered `FORMERR`.
- **Nearest first, never alone**: the answer is the two healthy servers nearest the visitor, nearest first, and every other one within 500 km of the nearest. So it always holds at least two when two are healthy, and every server about as near as the nearest; servers within 50 km of each other are shuffled among themselves, so they share the visitors. Each address family is ranked on its own: an `AAAA` answer ranks the servers that have IPv6.
- **Health always wins.** The places only order the servers health already chose: the table the agent hands its name server lists the healthy servers one by one with their places, and the name server refuses a table whose places name an address the answer does not, or leave one out. The last agreed set (a split, a start) is ranked the same way.
- **The address database is DB-IP "IP to City Lite"** (CC BY 4.0: free, redistributable, attribution required). Rejected: MaxMind GeoLite2 (free, but its licence needs an account and a key per install and forbids redistributing the file, so a host offering Deplo could not ship it).
- **It ships with each release and is updated by updating Deplo** (amendment 3, owner's decision 2). The release workflow (`docker-image.yml`, `scripts/geo-table.mts`) reads DB-IP's download page for that month's CSV, its SHA-1 and its record count, downloads it and checks the SHA-1 of the content and the count, every range in order with no gap from the first address to the last of each family, every place on the globe, and that `8.8.8.8` is in the US. It reduces it to the **location table**: IPv4 in /22 blocks and IPv6 in /40 blocks, each at the whole-degree place that covers most of it, about 7 MB, 3 MB compressed, with a SHA-256 of its own; and a list of the 25,000 cities with the most IPv4 addresses for the picker (0.4 MB). The image carries both under `/app/geo` with a manifest that names them by digest; the release attaches them as assets. **When the download or a check fails, the release reuses the newest release's copy** (checked the same way) and says so in its log; the manifest names the release it came from. A release with neither fails.
- **No server fetches it.** Deplo checks the table at start and hands it to each agent that says Hello `dns.geo` with `SetGeoTable` (gzip'd, named by its digest), when the agent's reply to `SetClusterZone` names another one. The agent checks it whole and keeps it on disk, and hands it to the name server **as a descriptor opened for reading**, beside the sockets: the process reads it once at start and can neither write it nor open anything by path. A new table restarts the process on the same sockets. A table that does not hold together is refused, and the name server answers every healthy server.
- **The credit and the date are visible** (owner's decision 2). **Server locations** shows "IP geolocation by DB-IP" linking to db-ip.com and the table's month, and says "over three months old: update Deplo for a newer one" past three months; the manual says the same, and the third-party notices carry the credit. A build with no table says every healthy server is answered.

### Certificate checks over DNS (phase 3)

The owner's four decisions of 20 Nov 2026:

1. **A wildcard by default for a zone delegated to the cluster.** Nothing is ordered for an empty zone; `<zone>` and `*.<zone>` are ordered together when the first domain inside the zone needs HTTPS, and from then on every name one label below is served by that certificate with no order of its own. A name deeper than one label gets its own, over DNS. **DNS zone -> Advanced -> One certificate per zone** turns it off: each name then gets its own over DNS. July's "no certificate by default" does not apply here.
2. **Ordered once per zone, never per server.** One server renews it (`cluster_zone_certs.renewer_server_id`): its proxy orders through the `deplo-dns` resolver, Traefik's HTTP-request provider calling its own agent. The agent reads the pair from the proxy's store as ADR-0048 does and hands it back to Deplo with its key (only when Deplo holds another one); Deplo takes it from the renewer only and keeps it sealed, and every other server gets it as a file in its routes file. A renewer unreachable for 10 minutes, emptied or gone is replaced by the server that joined longest ago; the new one gets the valid pair, puts it in its proxy's store under `deplo-dns` at its next quiet restart, and orders nothing while it is valid. The renewer's order router exists only while its store holds a valid zone pair, or no valid one exists anywhere, so the duplicate limit (5 per name set per week) is never at risk.
3. **A name outside the zone** shows one optional `_acme-challenge.<name>` `CNAME` into the zone, checked by Deplo every minute and by **Check**. With it, the name's own certificate is checked over DNS; without it, HTTP-01 exactly as before.
4. **Out of scope: #228** (a certificate on every server that runs a replica). Replica placement and failover do not change. Since decided in [ADR-0048](0048-a-cluster-domain-answers-on-every-server.md) step 5: a name's own certificate over DNS follows decision 2's model too.

How a check is set:

- **The endpoint** listens on `127.0.0.1:8444` inside the proxy's own network namespace (the agent opens the socket there), so no App container and nothing on the network reaches it, and asks HTTP basic auth with a secret only the proxy's compose mounts (`dns-challenge.secret`, 0600, read-only in the proxy). It takes only `_acme-challenge` names of this cluster's checks, inside its zones, and a value shaped as a key authorization digest.
- **Every server answers it within a second.** The agent sends its whole set of checks to every other member over the private network (verb `TXT`, a sequence number per sender); a member takes only names its sender owns in Deplo's list, and a refusal fails the order before the CA asks, the record taken back. A member it cannot reach does not hold the order up. Name servers answer `TXT` at `_acme-challenge` names with a 5 s TTL; a server that hears too few of its cluster answers `SERVFAIL`, as for every other record.
- **The proxy change** is static: the `deplo-dns` resolver copies the proxy's own account flags, plus `LEGO_DISABLE_CNAME_SUPPORT` (the agent maps a name to its CNAME target itself). One restart per server, one server at a time, only on servers of a cluster with a zone and an agent that says Hello `dns.challenge`; a server leaving the zone loses it. Until every reachable member can check over DNS, every name stays on HTTP-01.
- **Where a domain's mode lives**: `domains.cert_challenge` (`zone`, `dns` or null), written by the zone's pass and read by the route render: `zone` routes with no resolver of its own, `dns` with `deplo-dns`. A domain whose mode changes is routed again; a reroute that fails puts the mark back for the next pass.
- **A certificate the name already holds follows its mode** (#273): Traefik renews a stored entry through the resolver that holds it, so an entry whose names are now checked over DNS (its CNAME added, or the switch turned off) moves under `deplo-dns`, and one checked over HTTP again moves back, at the proxy's quiet restart before the entry's window, as an installed pair goes into the store. Its next renewal is then checked the new way, and nothing restarts outside that.
- **After each renewal the renewer closes its account's authorizations for the zone** (it asks for an order of the zone's names, which brings back every authorization the CA would reuse, and deactivates them). A server that stops renewing, and comes back with the zone's pair in its proxy's store, then cannot renew without a DNS check, which the other servers refuse (found on the lab). Which authorizations an order brings back is the CA's policy, not RFC 8555's, so this alone does not close it: the boot hold below does.
- **A server that comes back orders nothing the cluster did not ask it for, whatever the CA's reuse policy** (21 Nov 2026, the phase 3 duplicate and #266). Traefik renews every store entry inside its window the moment it starts, before the agent has heard anything, and a reused authorization needs no check at all. So the proxy never starts with such an entry: `deplo-proxy-hold.service`, a oneshot the agent installs with `Before=docker.service` and `RemainAfterExit` (once per boot, a failure delays nothing), runs `deplo-agent proxy-hold`, which moves every pair under `deplo-dns` and every pair of a hostname this server passes on from the store into the routes file, and takes out the routers that would order one. A file is served and never renewed, and it stops a new order for the names it covers (ADR-0048's lab). Once running, the agent puts a pair back, and drops one, only on word heard since it started: a zone's role from Deplo's `SetClusterZone`, an App's from a current lease that places it here with no return under way. An expired held pair stays while a copy of its App left running here could still ask for one. Rejected: deactivating a renewer's ACME account when its renewals are done (RFC 8555 §7.3.6), which needs that account's key on another server while the old one is away, and cannot cover #266, whose account also renews the server's own Apps; holding the proxy itself until the agent runs, which ties the panel's own address to the agent at every boot.
- **The key** never appears in a log, Activity, a failover bundle or the panel; names the zone's certificate serves are left out of the App's failover bundle, since every server holds it already.

### Times

| What                                  | Default | Range         | Why                                                              |
| ------------------------------------- | ------- | ------------- | ---------------------------------------------------------------- |
| A / AAAA of an App's name             | 30 s    | 10 s to 300 s | How long a resolver keeps naming a server that stopped.          |
| A stopped server leaves the answer    | 10 s    | 5 s to 60 s   | Five missed "alive" messages on the private network.             |
| Negative answers (SOA minimum)        | 30 s    | fixed         | A name added a moment ago appears quickly.                       |
| NS and glue                           | 1 day   | fixed         | The registrar's side; it changes only when a name server leaves. |
| NS and glue Deplo keeps in Cloudflare | 1 hour  | fixed         | Deplo rewrites them itself when a name server leaves.            |

So a server that stops leaves the answers within 10 s, and leaves every resolver within 40 s; meanwhile a browser that tries it falls back to the next address after a few seconds (ADR-0048, "Deplo down is a degradation"). Both values are per cluster, in the cluster's settings, behind Advanced.

### DNSSEC: out of scope

The zone is served unsigned, and the delegation must carry no `DS` record (the screen checks it). Signing on every server needs the zone's signing key on every server, or a scheme to hand signatures around that no one server can forge; that is its own decision, with a key-at-rest story like ADR-0045's. Nothing here closes the door: signing can be added to the same answers later.

## Phases

1. **Health-aware answers, no geography.** The unprivileged name server and `SetClusterZone`; the `native` backend in the domain screen with the delegation check; the majority and the last agreed set; the two times in the cluster's settings. The agent ships first behind `dns.zone`, then the panel.
2. **Geography.** Server locations, the DB-IP table shipped in the image and handed with the zone, ECS or the resolver's address, nearest-first answers. The agent ships first behind `dns.geo`, then the panel.
3. **Certificate checks over DNS (DNS-01).** `_acme-challenge.<name>` points into the zone (a `CNAME` once, or nothing for a name inside it), and each agent serves, on its proxy's own loopback, the endpoint Traefik's HTTP-request DNS provider calls to set a TXT record; the agent hands it to every other name server over the private network within a second. No DNS provider's token reaches any server. It reopens what ADR-0048 rejected: wildcard certificates, one per zone, ordered once. The agent ships first behind `dns.challenge`, then the panel. A certificate on every server that runs a replica (#228) stays out of scope.

## What the lab showed (phase 1)

Released agent v0.5.3-canary.17, panel v0.8.2-canary.47, leader v0.1.0-canary.7; three servers, `lab.test` delegated to them through a lab resolver (unbound with a stub zone, since the lab owns no public domain), default times (removal 10 s, TTL 30 s). A prober on the LAN asked each name server and the resolver every 0.5 s.

- **Normal answers**: 160 of 160 named exactly the three servers, from each name server and through the resolver; A, AAAA and NS as specified.
- **A server powered off** (three runs): it left each other name server's answers 9.4 to 11.0 s after the cut (the removal time, plus up to one 2 s "alive" interval), and the resolver's after 21.2 to 21.7 s, when its cached answer expired; never an error or an empty answer from a healthy server.
- **A server isolated from the others** (three runs): it answered `SERVFAIL` 11.5 to 12.0 s after the cut, the other two dropped it after 10.0 to 12.0 s and the resolver after 20.7 to 21.2 s, and none of them ever answered an error. Back on the network, it was answering and named by every server again within 2 to 4 s.
- **The process on a lab server**: `nobody`, no supplementary group, no capability, `NoNewPrivs`, its root a directory holding only its binary, its own network namespace; on the server's own IPv4 and IPv6, beside Deplo's DNS cache on `10.201.0.1:53`.
- **An ADR-0048 failover** (power cut of the Apps' server), the non-regression check: the Volume App took writes on its new server about 41 s after the cut, the database never stopped, and no two copies took writes at once.
- **Seen, not a fault**: an agent's first seconds log "answers fail, hearing 3 of 3": just started with nothing agreed yet, it answers `SERVFAIL` for one removal time, as decided above.

## Before a stable release: four changes (21 Nov 2026)

The owner's four decisions after the #228 lab, each its own release but the last.

### A copy's port check needs nothing from the image (#281)

- **The check is the server agent's own program.** A copy that starts beside the live one (a replica, an App spread over the cluster, a zero-downtime deploy) waits for its port as before, but its health check runs `deplo-agent probe <port>`, the agent's binary, which the agent keeps in the stack directory's `.deplo-probe` and which the stack mounts read-only. It reads the container's own listening sockets, so an image with no shell (scratch, distroless, `traefik/whoami`) passes it. Hello `deploy.probe`; an agent without it keeps the shell loop.
- **Why a health check at all, rather than only the agent's ready check reading the port** (the issue's first option, read literally): the proxy sends visitors to a container with no health check as soon as it runs, so every deploy beside itself would drop the requests of an App that takes a moment to listen. Nothing else gates it. Traefik 3.7.17's passive health check counts the App's own 500s (one 500 took the only copy out, and the next second answered 503), and retries alone still failed 25%, 12% and 6% of the requests to a copy not listening yet with 2, 3 and 4 attempts. The agent's program is the port check that reads nothing from the image.
- **No fallback to the in-place deploy.** An image that never listens fails at the deploy's deadline as before, with the same message (an agent test measures both checks). The probe's mount is not the App's storage, so a copy that fails still leaves the live one alone.

### A DNS verdict never takes a serving domain off the routes

- **A check only ever adds a route.** A domain that served (`domains.ssl`) stays routed whatever a later check says: `misconfigured`, `pending`, a lookup that failed, a member whose address Deplo does not know. The verdict shows on the domain screen ("It keeps answering meanwhile") and in Activity, as before. It holds for every check: the cluster's own, the twice-a-day drift check and a person's **Check**.
- **Pending to valid adds the route**, and only then is the App routed again (#278's reroute, now kept for that one change). A person removing or renaming the domain still takes it off.
- **Why**: #278 made every status change reroute the App, and #280 removed one false `misconfigured`; any other wrong or transient verdict would again have rendered the stack without the domain on every server, a 404 Deplo made itself. A route that stays while DNS truly points elsewhere costs nothing: no visitor reaches it.

### A server back gets its copy again

- **The leader hands it back**, since it already moves the copies: a load-balanced App that keeps no data (the roster's `balanced`), one member running two or more of its replicas, another running none. Once that member has answered for **2 minutes** (`GiveCopyAfter`, longer than the longest removal time of 60 s), the highest replica of the most loaded member starts on it, and nowhere else, and is recorded there once ready. Activity: "lab-1 runs its own copy of web again: it has been back for 2 minutes".
- **No other copy restarts**: no order reaches another member. Until its copy is ready the server passes its visitors on (ADR-0048), then serves them from it.
- **The extra copy the failover started stays where it is** until the App's next deploy: stopping it would leave a moment where the proxy still sends visitors to a stopped container.
- **Its generated address waits for the server it names** while that one is a member of the cluster (found on the lab): every copy holds the name in its routes, so renaming the address after a failover restarted every copy on every other server. A load-balanced App's address answers again once its server is back; it is still renamed when that server leaves the cluster.
- A server that drops again within the wait gets nothing, and its wait starts over. A start that fails changes nothing and is tried again. An App that keeps data stays where the failover put it, as before.

### A server back is named once it is up (found on the lab)

- **A server that starts, or comes back after a silence of the removal time, is named by nobody, itself included, until it has been up for the removal time.** It counts for the majority meanwhile, as one being emptied does, and the last agreed set a name server answers while warming leaves it out too. On the lab the zone named a server about 2 s after it came back, while its proxy still showed its default certificate, then a 502: two to five visitor errors in the 3.5 s after each return. Agent v0.5.3-canary.25 (`dnszone.DecideHolding`).
- Rejected: asking its own proxy for a name's certificate, which needs a TLS handshake that skips verification; ten seconds cover what the lab measured with room to spare.

### Cloudflare in front of the zone

- Cloudflare proxies a new record by default, and a proxied `CNAME` into the zone puts Cloudflare in the cluster's place: visitors reach Cloudflare, never the nearest server. When every address the domain resolves to is Cloudflare's, the domain screen and Activity say so: "set its record to DNS only (grey cloud)".
- The manual's DNS zone page has **DNS at Cloudflare**: the subdomain delegated with `NS` records inside the Cloudflare zone, every record there DNS only, and a bare domain through Cloudflare's CNAME flattening, which keeps health but loses geography, since Cloudflare asks the cluster in the visitor's place.

### Under a domain connected to Deplo (22 Nov 2026)

Until now a cluster App's domain in a Cloudflare zone connected for Automatic DNS was always put on the App's own tunnel (`crud.ts`), so on an instance with Cloudflare connected neither this zone nor "Answer on every server" could ever be used for such a name: the owner hit it with `fise.pixelfederico.com`, a compose App with its database on a three-server cluster. The owner's six decisions:

1. **Two paths, one result.** With Automatic DNS for the parent domain, everything is automatic; without it, everything still works by hand, with the exact records and a check on screen at every step. The manual path behaves as before.
2. **Add domain offers "Let the cluster answer" (the default) and "Cloudflare Tunnel"** for a cluster App's name under a connected zone, with the same "Let the cluster answer" label the domain row already used. With the cluster:
   - **No zone yet: Deplo makes one** under the connected zone, the first of `cluster`, `cluster-2`, ... `cluster-20` below it that no record in Cloudflare uses (the name itself or any name under it) and that overlaps no cluster's zone, so `cluster.pixelfederico.com` there. The cluster's settings show it, and **Rename** changes it (below). Deplo writes the zone's `NS` and glue in Cloudflare (`cluster_dns_zones.provider_id`, every record commented `Deplo cluster zone`, TTL one hour), starts the name servers (`syncClusterZone`) and checks the delegation, up to six times two seconds apart while Cloudflare's edge catches up.
   - **Then the domain's two records, DNS only**: the `CNAME` into the zone and the `_acme-challenge` `CNAME` (`domain_dns_records.acme_record_id`), and "Answer on every server" on. Nothing is typed. The domain is routed at once (`ssl`), so its certificate is ordered over DNS through the zone straight away.
   - **Making a zone is an instance admin's act.** For anyone else with no zone on the cluster yet, the default is the tunnel, and "Let the cluster answer" says an instance admin has to add the zone first; once one exists, their domains use it too.
   - **A domain is never left unanswered.** When the check fails (port 53 closed, a server not answering, a record missing) the domain goes on the tunnel, and its row says why (`domains.cluster_fallback`): "srv_3 (203.0.113.3) does not answer for cluster.example.com: open port 53, UDP and TCP, on that server". **Let the cluster answer** on the row (`moveDomainToCluster`) moves it once fixed, and so for any tunnel domain of a cluster App: Deplo swaps the tunnel's `CNAME` for the zone's in Cloudflare and lets the tunnel go when no domain is left on it. Visitors whose resolvers still hold Cloudflare's addresses may see errors for up to five minutes; the button says so. Anything the "Answer on every server" switch refuses (a path, past 200 Apps, a proxy with HTTP/3) and a team past its Let's Encrypt cap fall back the same way, with the reason.
3. **By hand, unchanged.** The zone's row says "Add its records where you bought the domain" and the records open as soon as a zone is added by hand, with copy buttons and **Check**; the domain's row shows its `CNAME` and the optional `_acme-challenge` one with **Check**. Found in the review and fixed: a domain answering on every server with records a person keeps listed only its App's server; its row now lists one record per healthy server of the cluster.
4. **A name inside the cluster's zone is never put on a tunnel**: asking for one is refused with the reason, and with no say over the zone it is still answered by it. Nothing is written in Cloudflare for it: the delegation covers it.
5. **ADR-0048's Cloudflare record backend is deleted** (`syncAtProvider`, one DNS-only record per healthy server). The forced tunnel, and the move of an App onto a cluster taking every connected domain onto its tunnel (`joinAppTunnel`), had left it reachable only for a domain in a second Cloudflare account; none existed on the owner's panel. A third choice would only add a worse one to Add domain: records Deplo rewrites lag a stopped server by a pass and stop following with Deplo down, place no visitor and know no App's server, where the zone does all of that with one `CNAME`. A domain that still has such records is checked as one written by hand, and its row says which records to change, or moves to the zone with **Let the cluster answer**.
6. **The App's own server first.** A name whose App runs on one server at a time (it keeps data, or the cluster does not load-balance it) is answered with that server first, then the other healthy servers nearest first, so a visitor does not detour through another server. A load-balanced App keeps nearest first. The answer table carries, per name, the member that runs its App (`ClusterZone.homes`, agent Hello `dns.home`; an older agent ignores it and answers nearest first), and Deplo pushes it whenever a placement changes who that server is (`recordPlacement`, every caller). Health still wins: the agent names a home only while it is in the answer, so an unhealthy server is never listed, and the others follow it with the same "never alone" rule, at least two servers when two are healthy. A stale home (a failover while Deplo is down) is still a healthy member that passes the visitor on (ADR-0048): one hop, never an error.

The domain rows say where its records are kept ("Deplo keeps its records in Cloudflare, pointed at the cluster's zone"), and **Use my own records** is not offered for them. A zone Deplo keeps cannot be removed while one of its domains is answered through it; **Rename** makes the new zone, rewrites the domains' records in Cloudflare (and says which ones a person must retype), then removes the old zone's records. An admin adding a zone in the cluster's settings under a connected zone gets the same automatic records. When the name servers change, Deplo rewrites the zone's `NS` and glue in Cloudflare on its next pass instead of asking for it in Activity. An App that leaves the cluster, or a cluster deleted, points each such domain back at the App's server with an address record, as Add domain does there, and a deleted cluster's zone records leave Cloudflare; renaming such a domain is refused with the way to do it (add the new name, remove the old), since its two records would stay behind.

Tested in CI only (`zone-automatic.test.ts` against an in-memory Cloudflare and fake parent name servers, `dns-zone.test.ts`, the agent's `home_test.go` and `cluster_zone_test.go`); no lab this round.

### A proxy restarts on one member at a time (22 Nov 2026)

At 18:11 UTC on 22 Nov the panel rewrote and restarted the proxies of eu-1, eu-2 and eu-3 within 11 seconds: each server linked again after the panel's update, and each link pointed its proxy at Let's Encrypt (ADR-0050 decision 16). fise answered nowhere for a few seconds. Decided by the owner:

1. **When Deplo restarts the proxy of a cluster member, it restarts that member's alone** (`rollProxyRestart`, `lib/data/clusters/proxy-roll.ts`, under every caller of `applyTraefikConfig`): it takes the member out of the zone's answers on every name server (the same mark as a member being emptied, handed again from the last zone table), waits one answer TTL, restarts the proxy, waits until the member's proven addresses answer on 443 with its proxy's own certificate and, for a name server, its port 53 answers its ident, puts it back, and only then lets the next member's restart start. Right after Deplo starts it first waits, at most 90 s, for the zone's first pass, so the restarts of every server linking at once drain too. A member that does not answer within 2 minutes is put back anyway, and the cluster's Activity says so.
2. **What a visitor sees**: an App that answers on every server sees no error, since no resolver names the member while its proxy is down. An App that runs on one server keeps the few seconds of its own server's restart: the other members pass its visitors to that server, which is the one restarting.
3. **A server in no cluster restarts as before.** A cluster without a zone still restarts one member at a time, with nothing to drain.
4. **Out of scope**: the restarts an agent makes on its own (a certificate's quiet hour, a moved App's certificate dropped), and the restart of every agent at once when it sets aside what another Deplo left, which happens once per machine.

## A certificate travels with its App, and members lost one after another (23 Nov 2026)

The owner's nine decisions after cluster eu. memos' timeline, rebuilt from the panel's Activity and the agents' logs: created on eu-3 at 20:08:17 and copied to eu-1 and eu-2 29 s later; eu-3 off at about 20:14:24, memos on eu-2 at 20:15:00; eu-3 back at 20:15:30 and off again at about 20:16:36; eu-2 off at about 20:17:04 while eu-3 was still off, so eu-1 alone heard one of three and nothing moved, as decided above; both back at 20:19. Its certificate came at 20:39:31: Deplo wrote the `_acme-challenge` CNAME in Cloudflare at 20:09:09, a second after Deplo's resolver had cached "no such record", which Cloudflare's zone says to keep for 30 minutes.

1. **A certificate travels with its App.** Every member holds each certificate an App's domains use, the zone's own or a name's own, as Deplo hands it with the zone (above). A member's report now replaces what Deplo thinks it holds, so a pair a member lost (eu-1 and eu-3 had fise's in neither their store nor their routes file) goes to it again on the next pass, within a minute. A failover start refuses on a member that holds no valid certificate for every domain whose certificate exists, the bundle's own pairs counted, and the leader tries the next member, so a moved App's first answer has its certificate (agent Hello `failover.certificates`). The `_acme-challenge` CNAME is read from the domain's own name servers, never a resolver's cache, so a name's certificate is ordered in the first passes after it is added.
2. **Replication starts at once**: an App's first copy starts the moment its bundle is stored, not on the watch's next pass ([ADR-0046](0046-replication-streams-member-to-member.md)). Until a member holds a whole copy the App cannot move there, as before.
3. **Replication is visible**: the App's page says "Copies: 2 of 2 up to date", "Copying to eu-2 and eu-3" or "Not copied yet: this App cannot move if eu-1 goes off", and under Advanced one row per member with its state, last copy, how far behind and size. Activity uses the same line.
4. **"Moving", not "offline"**: the leader announces a move the moment it decides it (event `moving`), and the App reads "Moving to eu-2" with the elapsed time until every one of its HTTPS domains answers on the new server with a certificate a browser accepts, at most three minutes. An App that cannot move says why: "Offline: no up-to-date copy" or "Offline: waiting for a majority of servers".
5. **Members lost one after another.** A member silent for **2 minutes** while the leader leads the others stops counting for the majority (`GoneAfter`, event `member_gone`), every renewal names it (`Order.Gone`), and a name server that a leading leader renewed within the removal time counts without it. So members lost one after another leave the last one serving: one of two is exactly half, and the leader holding Deplo's word for its epoch (the beat, `DeploFor`) keeps or takes the Apps, while that member's name server answers as a member of the side that is led. A gone member hosts nothing and votes again only once it has answered for 2 minutes and said what it removed (event `member_rejoined`). Two lost at the same moment still stop as above: one of three is no majority, and no leader takes anyone out. **Why 2 minutes**: a cut-off member stops its writers when its lease runs out, 5 s for a current agent, then at most the 21 s its stop takes (`fenceMargin`); an older agent keeps 60 s. Two minutes is past the slowest of these with room to spare, so a member that is only cut off has stopped its databases before the others stop counting it, and it is the 2 minutes a server back already waits (`GiveCopyAfter`). **The cost**: with Deplo unreachable during the second loss there is no tie-break, so nothing moves; and a member gone past the grace that comes back while the others are down cannot vote them back in on its own.
6. Decision 6 is [ADR-0050](0050-a-server-is-known-by-its-key-never-by-its-address.md)'s.

## A server back, and a new name (23 Nov 2026)

Three things cluster eu left unexplained on 23 Nov: an App that two lost members had fenced stayed down once they were back when its compose named no restart policy (the agent read a service with no `restart:` as `no`, and a fence stop exits 0, which `on-failure` never restarts either); a returning name server answered its old set for about 8 s; and a new name wrote "does not reach the cluster yet" a second before the zone answered it. Decided by the owner:

1. **When a member's lease is back, its agent starts again exactly the containers its fence stopped**, whatever their restart policy (agent `cluster-supervise.json` `fenced`, the containers that exited since the fence began). A stack whose lease went to another member meanwhile forgets them: it stays down and is cleaned up as before. A deploy, a start or the stack's removal forgets them too.
2. **Under a lease, a service with no restart policy is kept up** (`deplo.restart=unless-stopped`), so a crash or a power cut brings it back like any other. A policy the person wrote wins, `"no"` included, and a service another one waits to finish (`service_completed_successfully`) runs once as before.
3. **A returning name server names only what it hears now** (agent DeploCloud/deplo-agent#91). Just started, or thawed past 5 s of its own pushes, it used to answer its last agreed set from disk, servers it no longer hears included, for about 8 s. 4. **A new name's first check waits for its setup**: a domain answered by the cluster's zone that resolves to nothing within a minute of being added reads pending, writes nothing to Activity, and is checked once more when the minute is over, so only a real failure says "does not reach the cluster yet".

## A move goes leader first, the outage replayed, and what Deplo does not know (23 Nov 2026)

Decided by the owner after the tests above, shipped in panel v0.8.2-canary.74 (no agent or leader release: neither had changed):

1. **A move inside a cluster goes leader first.** A person's move between two members, and Deplo's own while it empties a server, records the new member, hands the leader the roster and waits until its snapshot places the workload there (`placeAtLeaderFirst`, at most 15 s), then deploys or, for a database, starts it there. Before, the deploy came first and every renewal stopped the new copy as placed elsewhere.
2. **Activity replays the outage.** When Deplo's machine stands in, Deplo keeps the stored leader's last applied event (`clusters.resume_event_seq`). Handing back replays that leader's buffer from there before the roster goes back (`replayBeforeHandBack`), adopts its moves, and every Activity line an event writes carries the event's own time (`activityAt`), never a time after now.
3. **Deplo says what it does not know.** While no member answers Deplo (`clusterOutOfReach`, since the last time any was heard), the cluster's banner reads "Deplo cannot reach this cluster since 08:22 UTC: its servers decide on their own", the stored warnings are kept as they were, an App reads `Offline: Deplo cannot reach its cluster since ...` and its Failover card shows its copies as of that time; lease changes from a leader standing in, "Not copied yet" and "cannot fail over yet" are not written. Activity says it once, dated when Deplo last heard the cluster, and says "Deplo reaches cluster eu again" when one answers.
4. **The 40 s after an heir's isolation was the lab's.** The cut and its removal were transient systemd timers with the default `AccuracySec` of one minute: the 61 s cut began 10 s late and ended 100 s after it was set. The network carried a renewal 1 s after the cut was really removed. The lab's timers now use `AccuracySec=100ms`.
5. **A copy installed as a new server is a new server on the cluster** (found below): the installer clears its network key and its leader's state with its old certificates, and Deplo never stores a network key another server holds; one that answers with it is asked to replace it in the same call.

## Test plan

**CI only, for every change** (each repo's own job, plus the cross-repo contract job ADR-0048 set up):

- `deplo-agent`: the name server in process on a loopback port, queried with the same library: answers for each record type, NXDOMAIN and REFUSED outside the zone, no recursion, no `ANY`, truncation and the TCP fallback for a long answer, response rate limiting, and a fuzzed parser path (malformed packets never crash it or draw a large answer). ## Considered options

- **Records at a connected provider (ADR-0048)**: kept at first as the backend for whoever already had one; deleted on 22 Nov 2026 (decision 5 above): under a connected domain this zone is made and kept by Deplo instead.
- **The connected domain's own tunnel for every cluster App's name** (until 22 Nov 2026): left neither this zone nor "Answer on every server" reachable on an instance with Cloudflare connected. It stays a choice, not the rule.
- **Hand-written records (ADR-0048)**: kept as the backend that needs nothing, with its limits stated.
- **The name server inside the agent's own process**: this ADR's first version, rejected by amendment 1. It is the only code on the server that parses packets from anyone, and inside the agent a single bug there would hold root, the Docker socket and the agent's key.
- **The name server in a container**: as isolated, but it would hang on Docker (an image to pull, a daemon that restarts) and need the host's network to see a visitor's address; the agent's own child process needs neither.
- **The name server in the leader**: rejected. One process on one machine answers for the zone exactly when that machine may be the one that stopped.
- **A separate DNS daemon (CoreDNS, PowerDNS) beside the agent**: rejected. A second program per server to install, update and supervise, and a config format to render, for what is one table and a few hundred lines; the agent's own binary, started unprivileged, gives the same isolation.
- **Health from the leader's leases**: rejected. Answers would stop changing whenever the leader is away, and two leaders in a split would disagree; the private network's own "alive" messages are on every server already.
- **A DNS service Deplo runs for every instance**: rejected. It would make every install depend on a service outside it, which the installable product must not.
- **The location database downloaded by each instance every month**: rejected for amendment 3's way. Every install would fetch from the internet on its own clock, an offline one never would, and two instances on the same release would place visitors differently.
- **MaxMind GeoLite2**: rejected for its licence, above.

## Consequences

- **Port 53 opens on the servers that answer for a zone.** It is authoritative only, rate-limited and served by a process with no privileges, but it is a new public port; a host that blocks it simply is not a name server.
- **The person types records once**, at the registrar, and the screen checks them; a name server leaving the cluster asks for that once more.
- **Answers can differ between name servers for a few seconds** (each sees the private network from where it stands); every answer is a set of servers that answer for the App, so a visitor reaches it either way.
- **More than half of a cluster stopping at once takes its zone down** until they return or are removed from the cluster: the price of never answering from the wrong side of a split.
- **A two-server cluster keeps naming a stopped server**: either one alone is exactly half, so it answers the last agreed set. Three servers is the smallest cluster whose zone drops a stopped one.
- **No DNSSEC** until a later decision.
