# ADR-0043: A cluster is led by its own leader, not by Kubernetes

**Status**: proposed; amended 23 Nov 2026 (the leader lives inside the cluster, below). Builds on [ADR-0006](0006-server-agent-is-a-per-host-go-binary.md) and [ADR-0040](0040-a-server-agent-links-to-its-control-plane.md).

Kubernetes is the usual answer to running Apps across several machines. The need underneath it is several machines that act as one: an App keeps answering when its server dies, and it can run on more than one server. Deplo gets that from a **cluster**: servers grouped together, which Apps and managed databases are placed on as if it were one server. The cluster decides which member runs each workload and moves it there (**failover**) when a member goes offline.

**Each cluster has a leader: a Go binary from its own repository.** It runs on one of the cluster's own servers, which Deplo picks (amended 23 Nov 2026, below; it first ran on Deplo's own machine). That lets failover keep working while Deplo is down. When a remote leader goes offline, a leader process on Deplo's machine leads the cluster until it returns. The leader picks members and orders moves. **It never builds compose files**: it re-sends to a new member the last stack the control plane built for that App, so AGENTS.md's rule that compose and routing logic never moves into Go still holds.

**The leader accepts no incoming connection,** like every server since ADR-0040. The way it reaches its members, which only connect outward too, is still open.

## Considered options

- **Kubernetes underneath, hidden from the user**: rejected. It needs every machine to reach every other one on a fast private network, while Deplo is built for servers that cannot reach each other. It would also replace the whole deploy layer, which is written for Docker Compose: rendering, routing labels, the network per Environment, the compose security checks and user-written stacks. It costs up to 2 GB of RAM for its control plane, and it still leaves traffic switching and data on a dead disk to solve.
- **Docker Swarm**: rejected for the same networking requirement, and because it accepts only part of the compose format.
- **The control plane as the only leader**: rejected. Failover would stop exactly when Deplo's own machine is down.
- **A leader elected among the members**: rejected. It needs members that can reach each other, and it puts the decision on machines that are themselves failing.

## Consequences

- To redeploy without Deplo, a leader needs an App's decrypted variables, which today only the control plane holds. What a leader may keep, and how it is protected, is decided separately.
- A remote leader and Deplo's machine can both be running, each cut off from the other. A leader therefore leads only while more than half of the cluster's servers answer it, or exactly half and Deplo does. Failover without Deplo needs more than half of the servers up: a two-server cluster that loses one while Deplo is down moves nothing, and its databases stop until Deplo is back (`docs/agents/cluster-rollout.md` §5).
- "Cluster" is the user-facing word. Nothing of Kubernetes is involved, and the Add dialog says so in one plain line.

## The leader lives inside the cluster, with a line of succession (23 Nov 2026)

On 23 Nov 2026 the provider of Deplo's machine lost connectivity for an hour; eu's leader ran there, so every member stopped its Apps with data until it was back. Decided by the owner:

1. **The leader lives on one of the cluster's own servers.** Deplo installs it on the member that reaches every other member directly and has the most free memory, once the members have reported a direct path (`leaderHome`, `placeClusterLeaders`, once a minute); a cluster led from Deplo's machine is moved there at the update that carries this. The picker offers the cluster's own servers only. Deplo's machine stays as the last stand-in. A leader an admin already put on a server outside the cluster stays where it is.
2. **A line of succession.** Every renewal names the line (`Order.Line`, heir first, then the next, `Order.Last` Deplo's machine): members Deplo named as heirs (`Roster.Heirs`: directly connected, an agent with Hello `cluster.succession`, at most two, in join order, and only while every member's agent pre-votes), less any the leader has not heard within 3 s. An heir it stops hearing leaves the next renewal and comes back at the end of the line. Each heir runs a leader of its own, standing by with the roster Deplo gives it (`leader.standby`) and the sealed bundles (ADR-0045).
3. **An heir takes over only with a quorum and a pre-vote.** Its agent asks the leader beside it to lead (`leader.succeed`) once its own lease went unrenewed for the removal time (`lease.PreVoteFor`, 10 s), 5 s more for each place down the line, never while the lease is extended for a planned restart. The leader then asks a pre-vote (`Order.PreVote`, which nobody takes), and probes with `Order.Succeed` only once a quorum said yes; a member refuses both while its own leader renewed it within the removal time, so a cut between leader and heir changes nothing, and an heir cut off alone takes nothing. A member gives each epoch to one leader only (`Order.From`). The quorum is the same rule as before. An heir honours extended leases as Deplo's machine does (§5), so the work of a dead leader's member moves after the plain fence when no extension was announced. Deplo adopts an heir that leads at its own epoch and replays its events from where that epoch began (`adoptHeir`, `ClusterView.since`); Deplo's machine, standing in, asks the same pre-vote.

**23 Nov 2026, later (ADR-0049, "A move goes leader first")**: a move between two members is handed to the leader before the deploy (`placeAtLeaderFirst`); handing a cluster back from Deplo's machine replays the stored leader's events from the last one Deplo applied (`clusters.resume_event_seq`) before the roster goes back; and while no member answers Deplo, Deplo writes no lease change a leader standing in reports. A second heir does not lead on its own when two of four servers are lost: exactly half, and Deplo's word goes only to the leader it stores, so Deplo's machine stands in.

## Deplo gives its word to the next in line (23 Nov 2026)

On eu with four servers, the leader's member and then the first heir's were powered off: exactly half was left, the second heir asked to lead but Deplo's word went only to the leader it stored, so Deplo's machine stood in after 74 s and fise and memos moved after about 2 minutes. Decided by the owner: **while the stored leader is silent, Deplo's beat names the epoch the first heir that tries to lead asks for** (`lineReach`, `nameHeir`), after the same 25 s since the stored leader was last named, so two halves never hold the word at once; one heir at a time, and a word taken back is not given again until it is over. That heir then leads exactly half, Deplo adopts it at its epoch as before, and **Deplo's machine stands in only when nobody in the line answers Deplo**. An heir that answers Deplo but does not ask to lead is still renewed by its leader, so nobody stands in for it either.

## Deplo adopts the next leader in about 30 s (23 Nov 2026)

On five servers, with the leader's member and the first heir's powered off, the next heir led 14.5 s after the second cut but Deplo adopted it after 80 s. Each call to a powered-off server waited 10 s for its link (`LINK_WAIT_MS`), and one supervision pass asked the stored leader, then probed every member in turn, then pushed rosters and told the old leader, before writing the line: ticks ran far past their 15 s. Now a server silent for longer than that wait fails a call at once (`linkFor`, as one a leader declared down), the stored leader and the line are asked together, the members are probed together, and the adoption is said as soon as it is stored.

On canary.76 live (ADR-0049), Deplo adopted eu-2 17.7 s after eu-1 was powered off, 3.5 s after eu-2 led. Two gaps showed with three servers: the server that takes over never counts the old leader's server as gone past the grace, since it never heard it, and the next heir starts with no gone set, so exactly half is never left after a second loss; and Deplo's machine standing in while it reached no server took the epoch the first heir led at, so Deplo handed the cluster back instead of adopting it (fixed in deplo#324, not released).

## What the leader knows travels with the line (23 Nov 2026)

On canary.76 with three servers, the leader's server and then the first heir's were powered off: nobody led, since the heir never counted as gone a server it never heard and the next heir started with no gone set, and Deplo, left without the line by the paths of the stopped servers, had its own machine stand in. Cut off from every server, that machine took epoch 65 and eu-3 took 65 too; back, Deplo handed the cluster to eu-2 at 66. Decided by the owner:

1. **Every renewal carries the leader's gone set and how long ago each member was last heard** (`Order.Gone`, `Order.Heard`), and the agent next in line hands both to the leader beside it (`SucceedAsk`), so the 2-minute grace never starts over at a takeover and a member the old leader lost is gone for the new one on the same clock.
2. **Deplo always knows the line**: whether every member pre-votes is what each agent last reported (`server_agent_capabilities`), not a live Hello a stopped server cannot give, and the heirs are the largest direct group among the servers that answer, so a stopped server never takes the line away.
3. **One epoch, one leader**: a member gives an epoch a named leader holds to no other named leader; an order that names nobody (a leader's own start, promotion or copy back) is taken at its epoch and keeps that epoch's leader. Agent canary.40 refused those unnamed orders too, so no App with data moved; canary.41 takes them. Deplo's machine takes no epoch while no server answers Deplo, and back on the network Deplo adopts the heir that leads at the highest epoch; it never moves a leader whose server is silent.
4. **A renewal never waits on the disk**: the agent's lease file and the leader's state files are written off the lock every renewal takes; a new epoch, and an extension, are on disk before the answer and the orders.
5. **Only true lines**: Activity dates an adopted heir's takeover when a quorum took its epoch (`ClusterView.ledAt`); a member the leader has not heard (`heard: false`) never "answers again", a fenced one is never taken back to "not responding", a leader still trying records no member state, nothing about a leader stepping down is said while Deplo reaches no server, and a line the agent or the leader writes on every tick is written once per change.
6. **A silent member keeps its pin and its key** (deplo#328, not released): the leaders a member takes orders from, and the leaders that hold the bundles, keep every member that does not answer at a push, beside the leader, the live heirs and Deplo's machine. A server that was off at a push kept a list without the next heir, so two heirs could not reach each other, and lost its key, so it later led with a stale bundle.

## A running App always answers (24 Nov 2026)

On canary.78 every live test still left an App down for more than 2 minutes, and memos answered 404 on every server for 14 minutes 44 seconds after one backup. Decided by the owner, and what each one turned out to be:

1. **A running App always answers.** The proxy (Traefik 3.7) reads every container when one starts, stops or changes health, drops one whose status is not `running`, a paused one too, and never reads again at an `unpause`. A backup paused the App and then started and stopped its tar helper: both reads saw it paused, and once a read raced past the unpause the App had no route until the next start or stop on that server (memos: 21:30:46 to 21:45:44, ended by the next backup). The copy now runs in one helper started before the pause and removed after the unpause (agent canary.42), and every server watches container events: an App unpaused after a read that saw it paused makes the proxy read again within 2 s. A relayed backup whose stream takes nothing for a minute stops its copy, and a copy its reader left is stopped at once: on canary.41 a stream that ended early left lab-web paused 4 minutes behind a blocked tar, until its 30-minute step timeout. The answer tables were already pushed again every 2 minutes.
2. **Every order the leader sends passes the agent's checks.** deplo-cluster's tests record one example of each kind of order the leader sends (`internal/leader/testdata/orders.golden.json`); deplo-agent serves each through `Serve` at the epoch the member holds from that leader. With canary.40's rule the test fails on 8 kinds. Each CI checks the other repo's copy.
3. **An extension lasts only as long as its step.** On canary.78's rollout each leader restart took about 4 s (eu-2, 17:09:09 to 17:09:13) while every member kept the announcement 370 s. Now, once every member took a plain renewal since the last extension, or was silent past the longest lease another leader may have given it, each renewal carries `noExtension` and the members forget what they heard announced (leader canary.17, agent canary.42).
4. **Deplo coming back changes nothing that runs.** fise's 23 s at Deplo's return were two recreates of its web container (17:38:52, 17:39:08): the zone's certificate pass started from stored states that said no server answered, found no member able to check over DNS, routed fise to HTTP-01, and the next pass back. A pass that hears no server keeps every name's check (canary.79). The 58 s from Deplo's word to the heir's quorum did not show in the leader's tests with the same losses; the leader now logs its tally while it tries.
5. **One true message while Deplo is cut off.** Every call that finds a cluster server offline while Deplo reaches no server of its cluster says `Deplo cannot reach cluster eu since 17:30 UTC: its servers keep running without Deplo` (`connectAgent`, `readAgent`); a backup keeps its own wording.
6. **Big temporary files on disk.** The image tar and syft's files go under `<data-base>/inventory`, removed after every scan; PGlite test snapshots live in the test run's own directory.

## Every App back within a minute (24 Nov 2026)

On canary.79 fise was back 64 s after its server's power cut, 87 s after a second loss, and 61 to 66 s with Deplo cut off; a backup paused an App about 20 s per 200 MB; a cluster said "OK for production" with an empty line; "Deploy anyway" only lifted the hold. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.43, leader v0.1.0-canary.18, panel v0.8.2-canary.80):

1. **Every App back within 60 s of a power cut, in every case.** Measured first, the waits were timers: the pre-vote and the probe each waited 2 s for the dead member, the fence margin was 21 s for a stop the agent did in 19 s at worst, starts ran one after another (lab-web waited 25 s behind fise), and Deplo named the next leader 35 s after the cut (two 15 s watch ticks, each waiting out a dead server's Hello, then the 25 s since its last beat). Now a pre-vote is over at a quorum; the agent kills a fenced stack's containers together and is done 11 s after its lease (`stoppedWithin` 16 s), and a leader waits 13 s past the lease for an agent Deplo knows has it (`Member.quickStop`); each App with data starts on its own after its member's databases, Apps without data still in one line so a member back mid-pass keeps them; Deplo beats every 2 s asking an 8 s word (`Beat.trustMs`), the leader answers how long it holds the word (`BeatReply.holdsMs`, an older and longer word included, 20 s from an older leader), and Deplo names the next leader that and 5 s after the last beat that left; a beat to a server unheard for two of the link's pings is a miss at once, a miss makes Deplo check that leader at once, and the heir's word leaves as soon as it is given. The phase table is in ADR-0049.
2. **A backup pauses an App only for a copy on its own disk.** The copier mounts a folder under the agent's data dir; while the App is paused it copies the volumes there (`cp -a`), the App runs again, and the archive is read from that copy, then the copy goes. Without room (the data, a fifth more and 512 MiB free) the pause lasts the whole copy as before and Activity says why (`BackupResult.held_why`). 200 MB paused 1.3 s; 2 GB 20 to 44 s, the speed of the disk.
3. **"OK for production" only with a full line.** The pass that would clear the warning names the heirs first (the minute's `keepLeadersHome`, then the roster) and keeps the warning until the leader's snapshot names every heir; Activity names them. Cut 0.7 s after that line, the heir led in 10 s.
4. **"Deploy anyway" deploys.** One click lifts the hold and starts the deploy once the old copy is stopped (at once when its server does not answer); Activity says "Accepted that ... starts without ...", then "Deployed ..." only once that deploy is ready, and for a silent old server only that Activity will say where its copy is kept once it answers.
5. **The early-closed relayed stream** was the destination's disk: eu-1 had 11 MB free on 23 Nov, its write ended first and the relay reported "the agent ended the backup without a result" while the source went on copying with lab-web paused. Now the source's copy is ended at once and the run says the destination's reason (seen live: `the destination server stopped taking the backup: write backup artifact: ...` on a 2 GB backup to a member with 2 GB free). **The prober's gaps** during the canary.79 rollout were this host's network: every request of those seconds completed at the same instant once the path came back (queued, not lost), while the event loop went on ticking; nothing in Deplo touches the host's network. On canary.80's rollout, watched with the gateway's neighbour state and pings every 0.5 s, there was none.

Found live and fixed on `main` (deplo#342), not released: **a bundle refresh by replication ran beside a reroute's**, so lab-web, whose domain was added while a 2 GB backup slowed the cluster, kept a bundle without its routes and answered 404 for 5 minutes 17 seconds after its server's power cut, until **Reload routing**; every refresh now waits its App's turn. Deplo's supervision and the line also read a server unheard for 5 s as away at once (Deplo's word came 19 s after the cut, not 13), and "OK for production again" names the heirs in the leader's order.

## A backup pauses only for what changed (24 Nov 2026)

On canary.80 a 2 GB App was paused 20 to 44 s for its backup, a canceled relayed backup went on copying until eu-1 was nearly full, adding a domain cut the Apps the other servers passed on for 1 to 2 s, and "Moved lab-web to eu-3" was written twice. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.46, panel v0.8.2-canary.83; the leader is unchanged at v0.1.0-canary.18):

1. **A backup pauses only for what changed.** The copier carries the agent's own binary: `deplo-agent stage-sync` copies the volumes on the App's disk while it runs, then, paused, copies only what changed since: a file whose size, time, mode or owner differ, or whose change time is after the first pass began, so a write that keeps a file's size and time is caught too, and what was removed goes. The first pass writes in 8 MB steps it waits on, at the lowest CPU and disk priority: canary.44 copied at page-cache speed, and on eu-1 (1 core, 2 GB) the agent could not renew its lease for 5.6 s, fenced the App it was backing up (down 12 s), and the 2 GB of writeback then stalled every App on the lab's shared disk for 20 s. A pass made in the pause no smaller than the first is said in Activity (`held_why`). On canary.83, lab-pause2 (2 GB, a writer rewriting 4 MB every 10 s) was paused **156 ms** and backed up to eu-2 in 9 minutes, with no App down. A second regression showed first: the relay's stall watchdog counted from the start, so the gentle first copy (about a minute for 2 GB) failed the backup as a stalled stream (`io: read/write on closed pipe`, canary.45); a stall is now a frame the stream takes nothing of for a minute.
2. **A backup never fills a disk.** Before it starts, Deplo measures what it will write (an App's volumes, a database's last dump) and asks the destination server for its disk: it starts only if a tenth of that disk stays free, else the run fails at once with `eu-2 has 2.0 GB free, too little for this backup (about 2.0 GB) and a tenth of its disk free, so it did not start` (seen live, refused in 1 s, nothing paused). The copy on the App's own disk must leave a tenth free too, the archive counted when it is written there. **A cancel stops both ends**: over an agent link `conn.close()` closes nothing, so canary.80's cancel only marked the run; now the cancel ends each call, a relay ends both sides as soon as either stops (cancel, timeout, lost stream), the destination removes its partial file when its call ends and the copier kills what still copies before its copy goes. Canceled live with 115 MB landed: the copier and its copy on eu-1 were gone 0.5 s later, the partial file on eu-2 1.8 s later.
3. **Adding a domain drops nothing.** Two causes. Every passed-on connection takes the forwarders' lock, and a new table held it while docker answered (an inspect per forwarder, then their processes and the list): on a busy server every App passed on through it waited 1 to 2 s; the docker side now runs under a lock of its own (`TestAnswers_aNewTableWhileDockerIsSlowHoldsUpNoConnection`). And the App whose domain is added has its container recreated for the new labels: compose creates the replacement beside it as `<old id>_<name>`, which the agent counted as starting, so every other server held that App's visitors 13 s while its own proxy kept answering (seen on canary.81); the waiting replacement no longer counts. On canary.82, a domain added to lab-pause2 cut no other App on any server, and lab-pause2 itself answered nothing for 1 s on every server, its own included, when its old container stopped.
4. **One line per event.** When a new server leads, the watch scheduler starts a watch on it while the one it aborted may still apply an event, and a move advances the stored sequence only once its batch settles: both applied `failed_over`, at the event's own time (03:20:56.106, twice). The same race wrote eight lines at once on 23 Nov (07:37:50). Each leader event is now claimed once per process. Every Activity line of this round's tests appeared once (112 lines, 112 distinct), a leader change included.
5. **Reachable by name within the minute.** Measured from Deplo's machine with eu-1 powered off (it ran no App): eu-2's and eu-3's name servers left it out after 9.1 and 10.1 s (the removal time, 10 s), the answers live 30 s, 1.1.1.1's caches named it until +27 s and this host's resolver until +30.2 s; `curl` by name never failed (it tries the next address), and the prober, which takes only the first address, failed 1 s. That is under the failover itself (40 to 55 s), so nothing changed. Repeated with Apps moving (canary.83): the name servers dropped eu-1 after 9.9 s, `fise.pixelfederico.com` stayed in this host's resolver about 35 s, so `curl` by name took 4 s (the dead address first) for about 25 s and failed twice; the prober by name failed 30 s for fise, which never stopped on any member. A shorter answer TTL (15 s) would halve that tail; it stays 30 s.
6. **A failover never starves its cluster** (found live on canary.82). eu-1, running lab-pause2 (2 GB, replicated), was powered off: its copy on eu-2, then on eu-3, was copied into the live volume at full disk speed, the lab's three servers share one disk, and the leader on eu-3 and every agent missed their renewals. eu-2 and eu-3 fenced fise, memos and lab-web (down 85 to 107 s), the zone answered nothing for 10 s, and eu-2 took over at epoch 86. On one filesystem a promoted copy is now renamed into place (agent canary.46), and its ready mark goes first, so a copy moved half way is never promoted again. Cut again on canary.83 with lab-cut's domain added 32 s before: lab-cut answered on eu-2 after 15 s (by name 20 s), lab-pause2 on eu-3 after 25 s (by name 32 s), memos and lab-web never stopped.

Released this round: agent v0.5.3-canary.44, .45 and .46, panel v0.8.2-canary.81, .82 and .83 (each later pair fixes what the one before broke live: .44's first copy at page-cache speed fenced an App on a 1-core server, .45's stall watchdog failed a 2 GB relayed backup). **Not fixed**: deleting an App while a member that held it was just back left that member's copy (2 GB, its container and a dated copy) and a failed failover start's promoted volume on another member, and a failed relayed backup once left a 184-byte artifact (its age header) committed on the destination; all removed by hand. A returning member's dated copy is still a full copy.

## A busy disk costs no lease (24 Nov 2026)

On canary.83 heavy disk work cost the leases twice: canary.81's first backup copy fenced an App on a 1-core server, and a failover's full-speed copy on the lab's shared disk made every lease run out (fise down 85 to 97 s). A failed relayed backup left a 184-byte file kept as complete, a deleted App left its copies on a member just back, and a returning member's dated copy was a full copy. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.47 and .48, leader v0.1.0-canary.19, panel v0.8.2-canary.84 and .85):

1. **A busy disk or CPU never costs a lease.** The agent's service takes `CPUWeight=1000 IOWeight=1000 MemoryLow=128M` at every start (runtime only), and the leader it runs with it; every helper container (backup copier, volume copies, set-aside copies) runs in `deplocopy.slice` (`CPUWeight=10`, `io.prio.class` idle) at a CPU share of 2; replication runs on a thread of its own at nice 19 and idle disk class and writes a rebuilt file 8 MB at a time, each step waited on and dropped from memory. Nothing on a renewal waits on a file: the agent's log goes through a pipe that drops lines rather than wait, the zone's, forwarders', network's and restart watch's state files are written in the background (`keepLater`), and the leader writes its events in the background and reads a bundle without the store's lock (its meta from memory). A new epoch is still on disk before a member answers: that is a vote, not a renewal. **The pre-release load test found the leader's half**: with only the agent changed, a 2-minute disk and CPU hog on eu-1 made the leader on eu-2 renew nobody for 7.8 s (an event appended in the renewal loop waited on the shared disk), every lease ran out, and fise was down about 105 s. With leader canary.19, three runs: no lease ran out, no fence, the zone always answered; once every member saw one renewal 3.3 to 4.6 s after the one before (09:52:23, cause not found: a sampler of the leader's threads in the next run saw none of them wait on the disk). A renewal that comes 2.5 s after the one before is now said in the agent's log.
2. **A backup is complete only when it is checked.** The 184-byte file: a relay that fails cancels the destination's call, and Node's http2 `close()` ends the stream's writable side (END_STREAM) before it sends RST_STREAM; with nothing queued, the destination read a clean end and kept what it had, the age header. A relayed backup is now sealed (`StoreChunk.Header.sealed`, capability `backup-store.sealed`): the stream ends with a trailer naming the source's size and sha256, written only after every chunk, and the destination keeps the file only when both match. Live: a send cut at 203 MB (canary.84) and at 120 MB (canary.85) by cutting the destination's link to Deplo left nothing on it, and the next backups (420 MB, 210 MB) landed with the run's sha256.
3. **Nothing is left behind.** A delete tears the App down on every server of its cluster with its volumes and its set-aside copies (`StackRef.drop_set_aside`, capability `teardown.set-aside`), the bulk delete too; a queued teardown keeps the volumes and the flag (migration 0279), no longer skips a stack with no container left, and runs at the next drain once its server answers again. What a failed failover start left (the stack and the volume its copy was promoted into) goes once a renewal places the App on the member it moved to. Live: lab-send deleted 5 minutes after eu-1 was back, nothing of it anywhere 35 s later; lab-load deleted with eu-1 off, eu-2 and eu-3 clean within 20 s, eu-1's copies gone 58 s after it answered.
4. **A returning member sets its copy aside with a rename**, falling back to a copy for what cannot be moved: 2.18 GB in 197 ms (eu-1, pre-release), 2.94 GB in 300 ms and fise's 48.7 MB in 227 ms (eu-3, canary.84).
5. **True lines.** A failed backup names the offline server and its role: `Backup of Fise failed: eu-1, this backup's destination, is offline.`, also when its link drops mid-send (canary.85); a deleted backup reads `Deleted a 2.0 GB backup of memos`.
6. **The 6 s silences** of a name server at canary.81's and canary.82's rollouts were its warming: a restarted name server answers nothing until it hears every server of its cluster (or the removal time is over), so it never names a stale set. Each time one peer, always paired with eu-1, was heard 5 s late: a first WireGuard handshake retried after WireGuard's 5 s REKEY_TIMEOUT. In this round's 12 restarts and the canary.85 rollout every first handshake was answered within 2 ms and each name server was silent 1 s, so which packet was lost was not caught. Unchanged.

**canary.47 broke live.** Its log pipe dup'ed a pipe onto stderr whose reader does not survive the self-update's `exec`: the agent it started died on its first log line by SIGPIPE, a stop systemd takes as clean, so nothing restarted it. eu-1, eu-2 and eu-3 stopped one after another from 10:11; memos was down by name from 10:15, fise and every name server from 10:19, until their agents were started by hand at 10:21:54. canary.48 puts the real log back before the exec and, first thing, gives a stdout or stderr nobody reads the journal again (`logpipe.Revive`), so the update from canary.47 itself went through: all four agents in 82 s, each name server silent 1 s. Also found and fixed: a cancel never reached a scheduled backup (the runs in flight lived in one bundle's module), so a canceled 2 GB backup went on until its copier was removed by hand. **Not fixed**: a returning member keeps its dated copy and receives a whole new replica beside it, so a 2.8 GB App filled eu-1 to 99% (its copy was removed from the App's page); and a disk saturated by something else still stalls the Apps whose own writes wait on it (fise 6 s by name under the live hog).
