# ADR-0043: A cluster is led by its own leader, not by Kubernetes

**Status**: proposed; amended 23 Nov 2026 (the leader lives inside the cluster, below). Builds on [ADR-0006](0006-server-agent-is-a-per-host-go-binary.md) and [ADR-0040](0040-a-server-agent-links-to-its-control-plane.md).

Kubernetes is the usual answer to running Apps across several machines. The need underneath it is several machines that act as one: an App keeps answering when its server dies, and it can run on more than one server. Deplo gets that from a **cluster**: servers grouped together, which Apps and managed databases are placed on as if it were one server. The cluster decides which member runs each workload and moves it there (**failover**) when a member goes offline.

**Each cluster has a leader: a Go binary from its own repository.** It runs on one of the cluster's own servers, which Deplo picks (amended 23 Nov 2026, below; it first ran on Deplo's own machine). That lets failover keep working while Deplo is down. When a remote leader goes offline, a leader process on Deplo's machine leads the cluster until it returns. The leader picks members and orders moves. **It never builds compose files**: it re-sends to a new member the last stack the control plane built for that App, so AGENTS.md's rule that compose and routing logic never moves into Go still holds.

**The leader accepts no incoming connection,** like every server since ADR-0040. The way it reaches its members, which only connect outward too, is still open.

## Considered options

- **Kubernetes underneath, hidden from the user**: rejected. It needs every machine to reach every other one on a fast private network, while Deplo is built for servers that cannot reach each other. It would also replace the whole deploy layer, which is written for Docker Compose: rendering, routing labels, the network per Environment, the compose security checks and user-written stacks. It costs up to 2 GB of RAM for its control plane, and it still leaves traffic switching and data on a dead disk to solve.
- **Docker Swarm**: rejected for the same networking requirement, and because it accepts only part of the compose format.
- **The control plane as the only leader**: rejected. Failover would stop exactly when Deplo's own machine is down.
- **A leader elected among the members**: rejected. It needs members that can reach each other, and it puts the decision on machines that are themselves failing.

## Consequences

- To redeploy without Deplo, a leader needs an App's decrypted variables, which today only the control plane holds. What a leader may keep, and how it is protected, is decided separately.
- A remote leader and Deplo's machine can both be running, each cut off from the other. A leader therefore leads only while more than half of the cluster's servers answer it, or exactly half and Deplo does. Failover without Deplo needs more than half of the servers up: a two-server cluster that loses one while Deplo is down moves nothing, and its databases stop until Deplo is back (`docs/agents/cluster-rollout.md` §5).
- "Cluster" is the user-facing word. Nothing of Kubernetes is involved, and the Add dialog says so in one plain line.

## The leader lives inside the cluster, with a line of succession (23 Nov 2026)

On 23 Nov 2026 the provider of Deplo's machine lost connectivity for an hour; eu's leader ran there, so every member stopped its Apps with data until it was back. Decided by the owner:

1. **The leader lives on one of the cluster's own servers.** Deplo installs it on the member that reaches every other member directly and has the most free memory, once the members have reported a direct path (`leaderHome`, `placeClusterLeaders`, once a minute); a cluster led from Deplo's machine is moved there at the update that carries this. The picker offers the cluster's own servers only. Deplo's machine stays as the last stand-in. A leader an admin already put on a server outside the cluster stays where it is.
2. **A line of succession.** Every renewal names the line (`Order.Line`, heir first, then the next, `Order.Last` Deplo's machine): members Deplo named as heirs (`Roster.Heirs`: directly connected, an agent with Hello `cluster.succession`, at most two, in join order, and only while every member's agent pre-votes), less any the leader has not heard within 3 s. An heir it stops hearing leaves the next renewal and comes back at the end of the line. Each heir runs a leader of its own, standing by with the roster Deplo gives it (`leader.standby`) and the sealed bundles (ADR-0045).
3. **An heir takes over only with a quorum and a pre-vote.** Its agent asks the leader beside it to lead (`leader.succeed`) once its own lease went unrenewed for the removal time (`lease.PreVoteFor`, 10 s), 5 s more for each place down the line, never while the lease is extended for a planned restart. The leader then asks a pre-vote (`Order.PreVote`, which nobody takes), and probes with `Order.Succeed` only once a quorum said yes; a member refuses both while its own leader renewed it within the removal time, so a cut between leader and heir changes nothing, and an heir cut off alone takes nothing. A member gives each epoch to one leader only (`Order.From`). The quorum is the same rule as before. An heir honours extended leases as Deplo's machine does (§5), so the work of a dead leader's member moves after the plain fence when no extension was announced. Deplo adopts an heir that leads at its own epoch and replays its events from where that epoch began (`adoptHeir`, `ClusterView.since`); Deplo's machine, standing in, asks the same pre-vote.

**23 Nov 2026, later (ADR-0049, "A move goes leader first")**: a move between two members is handed to the leader before the deploy (`placeAtLeaderFirst`); handing a cluster back from Deplo's machine replays the stored leader's events from the last one Deplo applied (`clusters.resume_event_seq`) before the roster goes back; and while no member answers Deplo, Deplo writes no lease change a leader standing in reports. A second heir does not lead on its own when two of four servers are lost: exactly half, and Deplo's word goes only to the leader it stores, so Deplo's machine stands in.

## Deplo gives its word to the next in line (23 Nov 2026)

On eu with four servers, the leader's member and then the first heir's were powered off: exactly half was left, the second heir asked to lead but Deplo's word went only to the leader it stored, so Deplo's machine stood in after 74 s and fise and memos moved after about 2 minutes. Decided by the owner: **while the stored leader is silent, Deplo's beat names the epoch the first heir that tries to lead asks for** (`lineReach`, `nameHeir`), after the same 25 s since the stored leader was last named, so two halves never hold the word at once; one heir at a time, and a word taken back is not given again until it is over. That heir then leads exactly half, Deplo adopts it at its epoch as before, and **Deplo's machine stands in only when nobody in the line answers Deplo**. An heir that answers Deplo but does not ask to lead is still renewed by its leader, so nobody stands in for it either.

## Deplo adopts the next leader in about 30 s (23 Nov 2026)

On five servers, with the leader's member and the first heir's powered off, the next heir led 14.5 s after the second cut but Deplo adopted it after 80 s. Each call to a powered-off server waited 10 s for its link (`LINK_WAIT_MS`), and one supervision pass asked the stored leader, then probed every member in turn, then pushed rosters and told the old leader, before writing the line: ticks ran far past their 15 s. Now a server silent for longer than that wait fails a call at once (`linkFor`, as one a leader declared down), the stored leader and the line are asked together, the members are probed together, and the adoption is said as soon as it is stored.

On canary.76 live (ADR-0049), Deplo adopted eu-2 17.7 s after eu-1 was powered off, 3.5 s after eu-2 led. Two gaps showed with three servers: the server that takes over never counts the old leader's server as gone past the grace, since it never heard it, and the next heir starts with no gone set, so exactly half is never left after a second loss; and Deplo's machine standing in while it reached no server took the epoch the first heir led at, so Deplo handed the cluster back instead of adopting it (fixed in deplo#324, not released).

## What the leader knows travels with the line (23 Nov 2026)

On canary.76 with three servers, the leader's server and then the first heir's were powered off: nobody led, since the heir never counted as gone a server it never heard and the next heir started with no gone set, and Deplo, left without the line by the paths of the stopped servers, had its own machine stand in. Cut off from every server, that machine took epoch 65 and eu-3 took 65 too; back, Deplo handed the cluster to eu-2 at 66. Decided by the owner:

1. **Every renewal carries the leader's gone set and how long ago each member was last heard** (`Order.Gone`, `Order.Heard`), and the agent next in line hands both to the leader beside it (`SucceedAsk`), so the 2-minute grace never starts over at a takeover and a member the old leader lost is gone for the new one on the same clock.
2. **Deplo always knows the line**: whether every member pre-votes is what each agent last reported (`server_agent_capabilities`), not a live Hello a stopped server cannot give, and the heirs are the largest direct group among the servers that answer, so a stopped server never takes the line away.
3. **One epoch, one leader**: a member gives an epoch a named leader holds to no other named leader; an order that names nobody (a leader's own start, promotion or copy back) is taken at its epoch and keeps that epoch's leader. Agent canary.40 refused those unnamed orders too, so no App with data moved; canary.41 takes them. Deplo's machine takes no epoch while no server answers Deplo, and back on the network Deplo adopts the heir that leads at the highest epoch; it never moves a leader whose server is silent.
4. **A renewal never waits on the disk**: the agent's lease file and the leader's state files are written off the lock every renewal takes; a new epoch, and an extension, are on disk before the answer and the orders.
5. **Only true lines**: Activity dates an adopted heir's takeover when a quorum took its epoch (`ClusterView.ledAt`); a member the leader has not heard (`heard: false`) never "answers again", a fenced one is never taken back to "not responding", a leader still trying records no member state, nothing about a leader stepping down is said while Deplo reaches no server, and a line the agent or the leader writes on every tick is written once per change.
6. **A silent member keeps its pin and its key** (deplo#328, not released): the leaders a member takes orders from, and the leaders that hold the bundles, keep every member that does not answer at a push, beside the leader, the live heirs and Deplo's machine. A server that was off at a push kept a list without the next heir, so two heirs could not reach each other, and lost its key, so it later led with a stale bundle.

## A running App always answers (24 Nov 2026)

On canary.78 every live test still left an App down for more than 2 minutes, and memos answered 404 on every server for 14 minutes 44 seconds after one backup. Decided by the owner, and what each one turned out to be:

1. **A running App always answers.** The proxy (Traefik 3.7) reads every container when one starts, stops or changes health, drops one whose status is not `running`, a paused one too, and never reads again at an `unpause`. A backup paused the App and then started and stopped its tar helper: both reads saw it paused, and once a read raced past the unpause the App had no route until the next start or stop on that server (memos: 21:30:46 to 21:45:44, ended by the next backup). The copy now runs in one helper started before the pause and removed after the unpause (agent canary.42), and every server watches container events: an App unpaused after a read that saw it paused makes the proxy read again within 2 s. A relayed backup whose stream takes nothing for a minute stops its copy, and a copy its reader left is stopped at once: on canary.41 a stream that ended early left lab-web paused 4 minutes behind a blocked tar, until its 30-minute step timeout. The answer tables were already pushed again every 2 minutes.
2. **Every order the leader sends passes the agent's checks.** deplo-cluster's tests record one example of each kind of order the leader sends (`internal/leader/testdata/orders.golden.json`); deplo-agent serves each through `Serve` at the epoch the member holds from that leader. With canary.40's rule the test fails on 8 kinds. Each CI checks the other repo's copy.
3. **An extension lasts only as long as its step.** On canary.78's rollout each leader restart took about 4 s (eu-2, 17:09:09 to 17:09:13) while every member kept the announcement 370 s. Now, once every member took a plain renewal since the last extension, or was silent past the longest lease another leader may have given it, each renewal carries `noExtension` and the members forget what they heard announced (leader canary.17, agent canary.42).
4. **Deplo coming back changes nothing that runs.** fise's 23 s at Deplo's return were two recreates of its web container (17:38:52, 17:39:08): the zone's certificate pass started from stored states that said no server answered, found no member able to check over DNS, routed fise to HTTP-01, and the next pass back. A pass that hears no server keeps every name's check (canary.79). The 58 s from Deplo's word to the heir's quorum did not show in the leader's tests with the same losses; the leader now logs its tally while it tries.
5. **One true message while Deplo is cut off.** Every call that finds a cluster server offline while Deplo reaches no server of its cluster says `Deplo cannot reach cluster eu since 17:30 UTC: its servers keep running without Deplo` (`connectAgent`, `readAgent`); a backup keeps its own wording.
6. **Big temporary files on disk.** The image tar and syft's files go under `<data-base>/inventory`, removed after every scan; PGlite test snapshots live in the test run's own directory.

## Every App back within a minute (24 Nov 2026)

On canary.79 fise was back 64 s after its server's power cut, 87 s after a second loss, and 61 to 66 s with Deplo cut off; a backup paused an App about 20 s per 200 MB; a cluster said "OK for production" with an empty line; "Deploy anyway" only lifted the hold. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.43, leader v0.1.0-canary.18, panel v0.8.2-canary.80):

1. **Every App back within 60 s of a power cut, in every case.** Measured first, the waits were timers: the pre-vote and the probe each waited 2 s for the dead member, the fence margin was 21 s for a stop the agent did in 19 s at worst, starts ran one after another (lab-web waited 25 s behind fise), and Deplo named the next leader 35 s after the cut (two 15 s watch ticks, each waiting out a dead server's Hello, then the 25 s since its last beat). Now a pre-vote is over at a quorum; the agent kills a fenced stack's containers together and is done 11 s after its lease (`stoppedWithin` 16 s), and a leader waits 13 s past the lease for an agent Deplo knows has it (`Member.quickStop`); each App with data starts on its own after its member's databases, Apps without data still in one line so a member back mid-pass keeps them; Deplo beats every 2 s asking an 8 s word (`Beat.trustMs`), the leader answers how long it holds the word (`BeatReply.holdsMs`, an older and longer word included, 20 s from an older leader), and Deplo names the next leader that and 5 s after the last beat that left; a beat to a server unheard for two of the link's pings is a miss at once, a miss makes Deplo check that leader at once, and the heir's word leaves as soon as it is given. The phase table is in ADR-0049.
2. **A backup pauses an App only for a copy on its own disk.** The copier mounts a folder under the agent's data dir; while the App is paused it copies the volumes there (`cp -a`), the App runs again, and the archive is read from that copy, then the copy goes. Without room (the data, a fifth more and 512 MiB free) the pause lasts the whole copy as before and Activity says why (`BackupResult.held_why`). 200 MB paused 1.3 s; 2 GB 20 to 44 s, the speed of the disk.
3. **"OK for production" only with a full line.** The pass that would clear the warning names the heirs first (the minute's `keepLeadersHome`, then the roster) and keeps the warning until the leader's snapshot names every heir; Activity names them. Cut 0.7 s after that line, the heir led in 10 s.
4. **"Deploy anyway" deploys.** One click lifts the hold and starts the deploy once the old copy is stopped (at once when its server does not answer); Activity says "Accepted that ... starts without ...", then "Deployed ..." only once that deploy is ready, and for a silent old server only that Activity will say where its copy is kept once it answers.
5. **The early-closed relayed stream** was the destination's disk: eu-1 had 11 MB free on 23 Nov, its write ended first and the relay reported "the agent ended the backup without a result" while the source went on copying with lab-web paused. Now the source's copy is ended at once and the run says the destination's reason (seen live: `the destination server stopped taking the backup: write backup artifact: ...` on a 2 GB backup to a member with 2 GB free). **The prober's gaps** during the canary.79 rollout were this host's network: every request of those seconds completed at the same instant once the path came back (queued, not lost), while the event loop went on ticking; nothing in Deplo touches the host's network. On canary.80's rollout, watched with the gateway's neighbour state and pings every 0.5 s, there was none.

Found live and fixed on `main` (deplo#342), not released: **a bundle refresh by replication ran beside a reroute's**, so lab-web, whose domain was added while a 2 GB backup slowed the cluster, kept a bundle without its routes and answered 404 for 5 minutes 17 seconds after its server's power cut, until **Reload routing**; every refresh now waits its App's turn. Deplo's supervision and the line also read a server unheard for 5 s as away at once (Deplo's word came 19 s after the cut, not 13), and "OK for production again" names the heirs in the leader's order.

## A backup pauses only for what changed (24 Nov 2026)

On canary.80 a 2 GB App was paused 20 to 44 s for its backup, a canceled relayed backup went on copying until eu-1 was nearly full, adding a domain cut the Apps the other servers passed on for 1 to 2 s, and "Moved lab-web to eu-3" was written twice. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.46, panel v0.8.2-canary.83; the leader is unchanged at v0.1.0-canary.18):

1. **A backup pauses only for what changed.** The copier carries the agent's own binary: `deplo-agent stage-sync` copies the volumes on the App's disk while it runs, then, paused, copies only what changed since: a file whose size, time, mode or owner differ, or whose change time is after the first pass began, so a write that keeps a file's size and time is caught too, and what was removed goes. The first pass writes in 8 MB steps it waits on, at the lowest CPU and disk priority: canary.44 copied at page-cache speed, and on eu-1 (1 core, 2 GB) the agent could not renew its lease for 5.6 s, fenced the App it was backing up (down 12 s), and the 2 GB of writeback then stalled every App on the lab's shared disk for 20 s. A pass made in the pause no smaller than the first is said in Activity (`held_why`). On canary.83, lab-pause2 (2 GB, a writer rewriting 4 MB every 10 s) was paused **156 ms** and backed up to eu-2 in 9 minutes, with no App down. A second regression showed first: the relay's stall watchdog counted from the start, so the gentle first copy (about a minute for 2 GB) failed the backup as a stalled stream (`io: read/write on closed pipe`, canary.45); a stall is now a frame the stream takes nothing of for a minute.
2. **A backup never fills a disk.** Before it starts, Deplo measures what it will write (an App's volumes, a database's last dump) and asks the destination server for its disk: it starts only if a tenth of that disk stays free, else the run fails at once with `eu-2 has 2.0 GB free, too little for this backup (about 2.0 GB) and a tenth of its disk free, so it did not start` (seen live, refused in 1 s, nothing paused). The copy on the App's own disk must leave a tenth free too, the archive counted when it is written there. **A cancel stops both ends**: over an agent link `conn.close()` closes nothing, so canary.80's cancel only marked the run; now the cancel ends each call, a relay ends both sides as soon as either stops (cancel, timeout, lost stream), the destination removes its partial file when its call ends and the copier kills what still copies before its copy goes. Canceled live with 115 MB landed: the copier and its copy on eu-1 were gone 0.5 s later, the partial file on eu-2 1.8 s later.
3. **Adding a domain drops nothing.** Two causes. Every passed-on connection takes the forwarders' lock, and a new table held it while docker answered (an inspect per forwarder, then their processes and the list): on a busy server every App passed on through it waited 1 to 2 s; the docker side now runs under a lock of its own (`TestAnswers_aNewTableWhileDockerIsSlowHoldsUpNoConnection`). And the App whose domain is added has its container recreated for the new labels: compose creates the replacement beside it as `<old id>_<name>`, which the agent counted as starting, so every other server held that App's visitors 13 s while its own proxy kept answering (seen on canary.81); the waiting replacement no longer counts. On canary.82, a domain added to lab-pause2 cut no other App on any server, and lab-pause2 itself answered nothing for 1 s on every server, its own included, when its old container stopped.
4. **One line per event.** When a new server leads, the watch scheduler starts a watch on it while the one it aborted may still apply an event, and a move advances the stored sequence only once its batch settles: both applied `failed_over`, at the event's own time (03:20:56.106, twice). The same race wrote eight lines at once on 23 Nov (07:37:50). Each leader event is now claimed once per process. Every Activity line of this round's tests appeared once (112 lines, 112 distinct), a leader change included.
5. **Reachable by name within the minute.** Measured from Deplo's machine with eu-1 powered off (it ran no App): eu-2's and eu-3's name servers left it out after 9.1 and 10.1 s (the removal time, 10 s), the answers live 30 s, 1.1.1.1's caches named it until +27 s and this host's resolver until +30.2 s; `curl` by name never failed (it tries the next address), and the prober, which takes only the first address, failed 1 s. That is under the failover itself (40 to 55 s), so nothing changed. Repeated with Apps moving (canary.83): the name servers dropped eu-1 after 9.9 s, `fise.pixelfederico.com` stayed in this host's resolver about 35 s, so `curl` by name took 4 s (the dead address first) for about 25 s and failed twice; the prober by name failed 30 s for fise, which never stopped on any member. A shorter answer TTL (15 s) would halve that tail; it stays 30 s.
6. **A failover never starves its cluster** (found live on canary.82). eu-1, running lab-pause2 (2 GB, replicated), was powered off: its copy on eu-2, then on eu-3, was copied into the live volume at full disk speed, the lab's three servers share one disk, and the leader on eu-3 and every agent missed their renewals. eu-2 and eu-3 fenced fise, memos and lab-web (down 85 to 107 s), the zone answered nothing for 10 s, and eu-2 took over at epoch 86. On one filesystem a promoted copy is now renamed into place (agent canary.46), and its ready mark goes first, so a copy moved half way is never promoted again. Cut again on canary.83 with lab-cut's domain added 32 s before: lab-cut answered on eu-2 after 15 s (by name 20 s), lab-pause2 on eu-3 after 25 s (by name 32 s), memos and lab-web never stopped.

Released this round: agent v0.5.3-canary.44, .45 and .46, panel v0.8.2-canary.81, .82 and .83 (each later pair fixes what the one before broke live: .44's first copy at page-cache speed fenced an App on a 1-core server, .45's stall watchdog failed a 2 GB relayed backup). **Not fixed**: deleting an App while a member that held it was just back left that member's copy (2 GB, its container and a dated copy) and a failed failover start's promoted volume on another member, and a failed relayed backup once left a 184-byte artifact (its age header) committed on the destination; all removed by hand. A returning member's dated copy is still a full copy.

## A busy disk costs no lease (24 Nov 2026)

On canary.83 heavy disk work cost the leases twice: canary.81's first backup copy fenced an App on a 1-core server, and a failover's full-speed copy on the lab's shared disk made every lease run out (fise down 85 to 97 s). A failed relayed backup left a 184-byte file kept as complete, a deleted App left its copies on a member just back, and a returning member's dated copy was a full copy. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.47 and .48, leader v0.1.0-canary.19, panel v0.8.2-canary.84 and .85):

1. **A busy disk or CPU never costs a lease.** The agent's service takes `CPUWeight=1000 IOWeight=1000 MemoryLow=128M` at every start (runtime only), and the leader it runs with it; every helper container (backup copier, volume copies, set-aside copies) runs in `deplocopy.slice` (`CPUWeight=10`, `io.prio.class` idle) at a CPU share of 2; replication runs on a thread of its own at nice 19 and idle disk class and writes a rebuilt file 8 MB at a time, each step waited on and dropped from memory. Nothing on a renewal waits on a file: the agent's log goes through a pipe that drops lines rather than wait, the zone's, forwarders', network's and restart watch's state files are written in the background (`keepLater`), and the leader writes its events in the background and reads a bundle without the store's lock (its meta from memory). A new epoch is still on disk before a member answers: that is a vote, not a renewal. **The pre-release load test found the leader's half**: with only the agent changed, a 2-minute disk and CPU hog on eu-1 made the leader on eu-2 renew nobody for 7.8 s (an event appended in the renewal loop waited on the shared disk), every lease ran out, and fise was down about 105 s. With leader canary.19, three runs: no lease ran out, no fence, the zone always answered; once every member saw one renewal 3.3 to 4.6 s after the one before (09:52:23, cause not found: a sampler of the leader's threads in the next run saw none of them wait on the disk). A renewal that comes 2.5 s after the one before is now said in the agent's log.
2. **A backup is complete only when it is checked.** The 184-byte file: a relay that fails cancels the destination's call, and Node's http2 `close()` ends the stream's writable side (END_STREAM) before it sends RST_STREAM; with nothing queued, the destination read a clean end and kept what it had, the age header. A relayed backup is now sealed (`StoreChunk.Header.sealed`, capability `backup-store.sealed`): the stream ends with a trailer naming the source's size and sha256, written only after every chunk, and the destination keeps the file only when both match. Live: a send cut at 203 MB (canary.84) and at 120 MB (canary.85) by cutting the destination's link to Deplo left nothing on it, and the next backups (420 MB, 210 MB) landed with the run's sha256.
3. **Nothing is left behind.** A delete tears the App down on every server of its cluster with its volumes and its set-aside copies (`StackRef.drop_set_aside`, capability `teardown.set-aside`), the bulk delete too; a queued teardown keeps the volumes and the flag (migration 0279), no longer skips a stack with no container left, and runs at the next drain once its server answers again. What a failed failover start left (the stack and the volume its copy was promoted into) goes once a renewal places the App on the member it moved to. Live: lab-send deleted 5 minutes after eu-1 was back, nothing of it anywhere 35 s later; lab-load deleted with eu-1 off, eu-2 and eu-3 clean within 20 s, eu-1's copies gone 58 s after it answered.
4. **A returning member sets its copy aside with a rename**, falling back to a copy for what cannot be moved: 2.18 GB in 197 ms (eu-1, pre-release), 2.94 GB in 300 ms and fise's 48.7 MB in 227 ms (eu-3, canary.84).
5. **True lines.** A failed backup names the offline server and its role: `Backup of Fise failed: eu-1, this backup's destination, is offline.`, also when its link drops mid-send (canary.85); a deleted backup reads `Deleted a 2.0 GB backup of memos`.
6. **The 6 s silences** of a name server at canary.81's and canary.82's rollouts were its warming: a restarted name server answers nothing until it hears every server of its cluster (or the removal time is over), so it never names a stale set. Each time one peer, always paired with eu-1, was heard 5 s late: a first WireGuard handshake retried after WireGuard's 5 s REKEY_TIMEOUT. In this round's 12 restarts and the canary.85 rollout every first handshake was answered within 2 ms and each name server was silent 1 s, so which packet was lost was not caught. Unchanged.

**canary.47 broke live.** Its log pipe dup'ed a pipe onto stderr whose reader does not survive the self-update's `exec`: the agent it started died on its first log line by SIGPIPE, a stop systemd takes as clean, so nothing restarted it. eu-1, eu-2 and eu-3 stopped one after another from 10:11; memos was down by name from 10:15, fise and every name server from 10:19, until their agents were started by hand at 10:21:54. canary.48 puts the real log back before the exec and, first thing, gives a stdout or stderr nobody reads the journal again (`logpipe.Revive`), so the update from canary.47 itself went through: all four agents in 82 s, each name server silent 1 s. Also found and fixed: a cancel never reached a scheduled backup (the runs in flight lived in one bundle's module), so a canceled 2 GB backup went on until its copier was removed by hand. **Not fixed**: a returning member keeps its dated copy and receives a whole new replica beside it, so a 2.8 GB App filled eu-1 to 99% (its copy was removed from the App's page); and a disk saturated by something else still stalls the Apps whose own writes wait on it (fise 6 s by name under the live hog).

## A self-update never takes a server down (24 Nov 2026)

On canary.84 the agent's own update to canary.47 stopped it on every server, and the rollout went on to the next one; a returning member kept its dated copy and also took a whole new replica (eu-1 at 99%); a restarted name server stayed silent until it heard every server; renewals came 3.3 to 4.6 s late once under load; memos answered 404 for 2 s at one backup. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.49, leader v0.1.0-canary.20, panel v0.8.2-canary.86):

1. **A self-update never takes a server down.** The agent's service restarts on any exit (`Restart=always`, 1 s, no start limit): install-agent.sh writes it, and an agent on a server installed before adds `deplo-agent.service.d/restart.conf` itself at start (uninstall removes it). A self-update keeps the binary before it (`deplo-agent.previous`, a hard link) and starts a guard from it in a transient unit of its own: the new agent must answer a Hello within 30 s, or the guard puts the previous binary back and restarts the service. A leader install keeps its previous binary too, and puts it back when the new leader does not answer on its socket within 30 s (the call fails `ABORTED`). The leader needs no unit: the agent supervises it and starts it again on any exit. The rollout moves on only once the updated server answers on the new version and, for a minute, keeps answering and stays `ok` in each of its clusters' leader snapshots (`rolloutTiming.holdMs`); a server that does not (`no_return`) stops the rollout, and that release is never tried on it again on its own: Retry now, a Hello on the pin or a new pin. canary.47 had reached all three servers because a retry that found the first one unreachable overwrote its `no_return`: the pause is now kept. The same holds for the leader rollout. CI runs the real path in a container whose PID 1 is systemd (`TestSystemd_`): the exec, the new run's first lines, a restart after SIGHUP and after exit 0, a binary that exits at once going back. Before the release the same test ran on a clone of eu-1 from the real canary.48 binary, and the agent stayed up on the build for 5 minutes. Live results in ADR-0049, "What cluster eu showed" (canary.86).
2. **A replica never fills a disk.** Deplo hands a member a copy only if, after it, a tenth of its disk stays free (the dated copies on it count, as they sit on the disk), from what the App's server measures and what the member says it already holds; a copy the member holds whole, or the App it runs, is never held back. The member's row and page show the warning icon with `eu-1 has 1.2 GB free, too little for a copy of shop (about 2.8 GB) and a tenth of its disk free. Free some space on it, and the copy starts.` (another team sees no App name). Live it did not hold twice (see ADR-0049), both fixed on `main`, not released: a member back from a power cut started the new copy from the table it kept on disk before Deplo's next pass (deplo-agent#117: no new copy before Deplo hands a table in this run), and a copy that began while its App was still small passed the check and grew with it (deplo#359: a copy not whole yet is held back whenever the disk would be under a tenth free).
3. **A restarted name server answers on a majority** (ADR-0049): it answers once it hears more than half of its servers, itself included, naming only those it hears. Live it answered 1.37 s after its agent restarted with one server unreachable: the zone decides once a second; while warming it now decides ten times a second (deplo-agent#116, on `main`, not released).
4. **Renewals on time under load.** Four causes, found one after another in the pre-release load runs on a clone: the leader's round waited for its slowest member, up to 2 s per pass, before the next could start, so one starved member delayed every member's renewal (the 3.3 to 4.6 s of 09:52:23, on all three at once): a round now waits 300 ms past a quorum and never sends a member a second order while one is in flight (`TestASlowMemberHoldsUpOnlyItsOwnRenewal`); replication ran at nice 19 on a 1-core server, where a starved thread keeps Go's only scheduler slot and every goroutine waits for it: copies now yield only the disk; three copies of a 2.2 GB file filled a 2 GB server's page cache, its agent went to swap and missed 7.1 s of renewals: what a copy reads leaves memory as it goes; and every renewal unsealed from disk the bundle of each copy a member keeps or receives, which waited 14.7 s on the saturated disk for two members (fise and memos fenced on eu-2, fise down 65 s by name): the bundle's Keep is now held in memory. A renewal more than a second late is logged. Last pre-release run and both live runs on eu-1 (1 core, two busy loops and a 1 GB file synced again and again for 2 minutes while a 2 GB App copied): no renewal more than a second late on any member, no lease ran out, no fence.
5. **memos' 2 s 404 was Deplo's.** fise-db's health turns `healthy` again about 10 s after its own backup pause; at 11:00 fise's backup ran first, and that event landed inside memos' 708 ms pause: the proxy read the containers, dropped the paused memos, and applies a new configuration at most every 2 s. A backup now freezes the App's processes through their cgroup, so Docker and the proxy still read it as running and it keeps its routes; Docker's pause stays the fallback (cgroup v1, or a freeze that fails).

Also found and fixed on `main`, not released: a Retry now runs outside the rollout pass, and the pass updated the next server while the retried one was still in its minute (deplo#358). **Not fixed**: the left copy a returning member saves to a backup destination on another member skips the room check (eu-2 reached 8.4% free with a 2.8 GB one); a left copy that finished saving 3 s after its App was deleted stayed as a backup (removed with its own delete); placement ignores free disk (two new Apps landed on the member with the least room); a SIGPIPE sent from outside is ignored by the agent, as by any Go program (only its own write to a dead output killed canary.47); an exit 0 is restarted 1 s after it, but the drain before it takes up to 5 s; and Apps whose own writes wait on the lab's saturated shared disk still stall (fise up to 6 s by name in a pre-release run).

## No copy fills a disk (24 Nov 2026)

On canary.86 copies that did not fit still filled disks (eu-3 91%, eu-1 92%) with no warning, a set-aside copy saved on another member had no room check (eu-2 at 8.4% free), placement ignored free disk, a destination cut mid-send kept its `.partial`, a copy saved 3 s after its App was deleted stayed as a backup, and a restarted name server answered after 1.37 s. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.50, leader v0.1.0-canary.21, panel v0.8.2-canary.87 and .88):

1. **No copy fills a disk.** The agent stops every copy it writes once its disk is down to a tenth free, by what the disk lets it write (`room`, a look every 8 MB): a replica, a backup or set-aside copy kept for another server, a backup's copy on the App's disk, a volume copied from another server, a dated copy that cannot be renamed. The member that keeps backups says its room with SEND, so a set-aside copy that does not fit is never read. A replica stopped for room says so until a whole snapshot lands; Deplo then holds it back, hands it again only with a fifth more room, shows the warning icon on the server's row and page with the App and its size, and Activity says it once; a backup refused or stopped for room shows there too. **Why no icon showed on canary.86**: nothing was refused (one copy started from a returning member's table on disk, deplo-agent#117; one passed while its App was small, #359). **canary.87 counted the blocks kept for root as free** (5% of the disk): on eu-4 a copy that did not fit was handed, written up to the agent's stop, removed and handed again every 80 s. canary.88 reads free space from the share the agent reports, as the agent counts it. Live on .88: eu-4 at 79.3% back from a power cut, lab-fit 1.6 GB: its copy never started, eu-4 stayed at 80%, the row read `eu-4 has 2.7 GB free, too little for a copy of lab-fit (about 1.6 GB) and a tenth of its disk free. Free some space on it, and the copy starts.`, said once in Activity. On a clone before the release, a replica of an App growing to 1.6 GB stopped at 1.475 GB free of 14.69 GB (89.96%; `df` rounds it up to 90%).
2. **Placement counts free disk.** Deplo hands the leader each member's disk and the Apps it holds whole (roster, place requests) and what an App's data takes (bundle meta); nothing is placed, moved or failed over onto a member its data would leave under a tenth free (`no_disk`). Live: eu-1, running lab-fit, powered off with eu-4 at 79.3% and no copy: lab-fit ran on eu-3 21 s after the cut and eu-4 got no start order; a move by hand to eu-4 was refused with `eu-4 has 2.7 GB free, too little for lab-fit's data (about 1.6 GB) and a tenth of its disk free.` eu-1, back at 79.4%, kept its dated copy (a rename), saved what it held to eu-2 as "Left on eu-1", and was refused the new copy; Activity said all three.
3. **Nothing half-written survives.** A server that keeps backups removes the partial files of a run that ended, at its start and before it takes a copy; a delete cancels its target's running backups; a backup that lands after its target went is removed, and so is what a returning member saves of a workload gone or being deleted. Live: eu-4 power-cut with 204 MB of a backup landed: no partial once back, and the next backup (629 MB) landed; lab-del deleted at 152 MB of a relayed backup while its copies ran: nothing of it on any member 43 s later. On canary.86 lab-grow's backup ended 2 minutes after its delete and stayed on eu-1 (1.68 GB), and its volume stayed on eu-3, mounted by that backup's copier during the teardown; both removed by hand.
4. **Name servers within 1 s.** A new run of the private network greets each new peer at once, so a restarted name server hears its majority within a round trip instead of at its peers' next alive (every 2 s). Live: eu-3's agent restarted with eu-1 cut from it: silent 0.26 s, answering 0.39 s after the restart.

**Not fixed**: a copy of a big file that changes is rebuilt beside the old one, so it needs twice that file's size while it is made; a copy's `bytes` counts every rebuild, so Deplo's estimate of what a copy still needs runs low (the agent's stop holds); a new App's data is unknown at placement, so two lab Apps landed on a member at 80% and wrote 1.6 GB there; a move under load cut fise and memos through eu-3 for 24 s (direct only, never by name).

## Copies go server to server, last (24 Nov 2026)

On canary.88 a 600 MB backup from eu-3 to eu-4 went through Deplo, so it crossed the lab's uplink twice, and fise and memos timed out by name while it ran; during a move eu-3 reached load 22 and fise and memos did not answer through it for 24 s; a copy of a big file that changes took twice its size with no check counting it; a copy's `bytes` counted every rebuild; and a new App, its data unknown, landed on the member at 80% and grew there to 90% with no warning. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.51, leader v0.1.0-canary.22, panel v0.8.2-canary.89):

1. **A copy between members goes direct.** Why it was relayed: `backupToDestination` sent every backup to another server's disk through Deplo (`relayBackup`), and a move copied each volume the same way (`copyVolumeBetween`); only what a returning member had left went over the cluster's network. Between two members of one cluster both now go member to member over the party (direct over the private network, the cluster relay only when no UDP path answers): Deplo names the file or volume to the receiving member (`ExpectClusterBackup`, `ExpectClusterVolume`), the sending agent dials it (`BackupRequest.member_fingerprint`, `SendClusterVolume`), sealed by size and sha256, and says `direct`, `relay` or `none`; on `none`, before a byte is read, Deplo relays as before. A backup run records its `path` (its row reads `sent server to server` or `sent through Deplo`), a copy row says the same from the agent's `relayed`, and a move's Activity line ends `, server to server` or `, through Deplo`. Relaying also starved an agent's link: at 18:45:44 lab-mv's 500 MB backup relayed to eu-2 held up eu-2's keep-alive, its link ended (`failed to wait for pong`) and the backup failed as `eu-2 ... is offline`. **The four uplink drops of canary.88**, against c36's disk and network logs, backup runs and Activity: 14:55:43 to 14:57:27 nothing crossed (no backup, move or relayed copy; Fise's and memos' replicas stayed on the LAN); 15:00:22 to 15:06:22 Fise's 6.5 MB backup through Deplo had ended at 15:00:21 and memos' 6 KB one had just started; 16:17:46 to 16:29:19 a copy was crossing: lab-send's 600 MB backup from eu-3 to eu-4 through Deplo, landing on eu-4 at about 5 MB/s since 16:17:31; 17:33:12 to 17:33:32 nothing crossed (lab-del's relayed backup was canceled at 17:31:43). Three of four had no copy behind them: the drops are the uplink's own.
2. **A member keeps answering while it copies.** Why load 22: the three members are LXCs of one Proxmox host and read its load (identical on all three), and their disk scheduler is `none`, so the copy slice's `io.prio.class idle` and `IOWeight` did nothing. Measured on canary.50, right after a 500 MB move landed on eu-3, eu-3's agent took 81% of its one core replicating the moved App (reading 569 MB/s from cache, then the userspace network's encryption to three members) while Traefik got about 13%: fise and memos through eu-3 timed out 17 s. Every copy now runs last by pacing (`internal/pace`): every docker pipe (backups, restores, moves, images), both ends of a replica and every store write look at the server every 8 MB or 200 ms, and while an App's container waited for the CPU or the disk, or an App's request crossed the agent, wait four times their last step (at most a second); the copy slice keeps at most 256 MB in memory, so what a helper writes never piles up for one flush. The first pacing looked only every 8 MB, and on the lab one 8 MB step of a stream took 5 s, so the capped wait let a copy run 83% of the time (agent still at 40 to 60%): looking every 200 ms too brought it to 29 to 35% on average, with fise and memos within 1.6 s by name during a 1.6 GB copy to three members.
3. **The space check counts the peak.** A file a copy rebuilds beside the one it replaces starts only if both fit a tenth free (`room.LeftFor`, the held size as the new one's); a copy not whole yet is handed only if a tenth stays free with its biggest file held twice (`VolumeUsage.largest_file_bytes`); a new stream drops what an earlier run left half rebuilt (an agent restarted mid-rebuild left 671 MB on eu-4); and a copy's size, on the App's page and in the room check, is its size on disk (`ClusterReplicaState.disk_bytes`), never the bytes sent. A file an App writes beside and renames in is a new file to the copy, not a rebuild: its size is known only as it lands, so the agent's floor at a tenth free is what holds it.
4. **A new App is placed where it can grow.** Create (App or database) asks the leader with `dataUnknown`: the member with the most free disk, never one over 80% used while another is under, the sibling rule first. A server whose disk passes 90% for any reason shows the warning icon on its row and card and **Disk almost full** on its page, naming its three biggest volumes and copies, and Activity says it once, in the team whose data takes the most (`servers.disk_full_at`, cleared under 88%).

Released this round: agent v0.5.3-canary.51, leader v0.1.0-canary.22, panel v0.8.2-canary.89, and canary.90 for agent updates that a slow GitHub made fail (ADR-0049, "What cluster eu showed"). **Not fixed**: three copies landing on one 1-core member at once still starved it: during lab-p1's backup to eu-2 (300 MB, direct) with two 300 MB replicas also arriving there, everything through eu-2 timed out, fise 137 s and memos 231 s by name, though their containers showed no stall of their own (each copy paces itself; their sum is not paced). A move's App is down for its whole copy, longer now that the copy is paced (600 MB: 6 min). A long member-to-member copy dies with its agent's link: eu-4's link was closed by the panel at 21:30:44 and the move rolled back (a retry passed). A file an App writes beside and renames in counts only at the agent's floor. A restore from another member still goes through Deplo.

## One copy at a time, and what a one-core server spends (25 Nov 2026)

On canary.90 fise was down 137 s and memos 231 s while eu-2 took a backup and two 300 MB replicas at once; a move rolled back when eu-4's link closed mid-copy; an App deleted just after a member came back left a 1.68 GB file on eu-1 and a teardown that failed three times at its deadline; and two name servers missed one probe together. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.52, panel v0.8.2-canary.91 and .92; the leader is unchanged at v0.1.0-canary.22):

1. **A member's Apps keep answering whatever copies it takes.** Why they went down: eu-2 has one core, and at rest under the lab's prober (a new TLS connection every second to every App on every address and through every member) it was already 50 to 67% busy (Proxmox's own counter for the LXC): its proxy terminates every request to fise and memos from all four servers, and every certificate had Traefik's default **RSA-4096** key, whose signature takes 11.6 ms of that core (86 per second; ECDSA P-256 22 530 per second), 16 to 38% of the core for the proxy alone; the agent ran 9 `docker` processes a second, mostly the same `ps` and `inspect` (a quarter of the core with dockerd); and the copies ran inside the agent, whose service has `CPUWeight=1000`, while the proxy had Docker's 100. With three copies the core reached 98 to 99%: the proxy's queue of handshakes grew faster than it drained, so requests waited 8 s and timed out, while fise's and memos' own containers had nothing to do. The overload holds itself up: it ended only when the load did (the backup's end in c37; a 20 s pause of the prober in c38). It came back in c38 with **no copy at all** (23:47:41, fise 82 s, memos 87 s): three new name forwarders and a replica resync after eu-4's agent restarted were enough, and at 23:55:51 one 300 MB replica into eu-2 took both down again (57 and 59 s). What changed:
   - **One copy at a time on each server, sent or received** (Deplo): a new replica starts only while neither end copies anything else, and a backup waits its turn the same way; a waiting copy reads **Queued** with what it waits for (`Queued: eu-2 is busy with a copy of lab-p1`; `Waits its turn: eu-2 is busy with a copy of lab-p1` on a backup run). A copy a member already holds goes on, and while it is behind (catching up on what its App wrote since) it still holds both ends; one that waits 30 minutes goes anyway. **A move never waits** (canary.92): canary.91 made it wait before anything stopped, but on a cluster the leader already holds the new member by then, so the old one had stopped the App, and two lab Apps were down for minutes with nothing copying them; a move now takes its turn at once and the others wait for it.
   - **The proxy level with the agent**: the agent writes its own weight (1000) into the proxy's cgroup at every start and whenever it restarts or recreates the proxy (Docker's `--cpu-shares` maps to a different weight per runc version: 26215 gave 1394 on eu-4).
   - **A copy backs off while the Apps keep waiting**: it looks every 50 ms (it was 200), and each step the Apps waited doubles its wait, from 4 to 32 times the step (at most 2 s), each step they did not halves it: a fifth of the server at first, a thirtieth under lasting pressure.
   - **A repeated docker read is answered for a second**, until the agent changes something: 71 to 48 docker processes per 10 s on eu-4, the agent's service from 30 to 19% of its core.
   - **ECDSA certificates**: every proxy Deplo installed orders P-256 keys (`acme.keytype=EC256`), new installs and, through the pass that moves Traefik to its pin, existing ones; certificates already issued change at their renewal (fise's and memos' in January).
2. **A dropped link does not kill a move.** Why eu-4's link closed on canary.90 is not known from what was kept: the agent logged only `link closed` and the panel nothing (no deploy, OOM or network event at 21:30:44 on this server). Both now say who ended it: the agent whether the panel closed it (its code and reason), the connection under it ended, or its own gRPC closed it; the panel its code, reason and how long since it last heard (on canary.91 every link that ended said `1006`, either at this server's proxy restart or when the lab's uplink went down). How it killed the move: the copy goes member to member, but the panel's connection to the receiving member was bound to the link that closed, and its next call failed with `14 UNAVAILABLE` (`connect ENOENT /tmp/deplo-link-deKWBS/15.sock`). canary.91 makes a move whose copy breaks on a link (Deplo's to either server, or the one between them) put the App back where it was, running, and move it again by itself once both servers answer, up to 3 more times, then roll back saying `Moving X to Y failed after 4 tries - it stays on Z: <why>`. **Live it did not hold** (both on canary.92, lab-pc 300 MB from eu-3 to eu-1, a link cut 30 s halfway): with eu-3's (the sender's) link cut, the rollback could not start lab-pc on eu-3, the server cut off, and that skipped the retry (`After 2 tries: Failed to copy lab-pc's data to eu-1 (14 UNAVAILABLE: Connection dropped)`, lab-pc down 653 s until started by hand); with eu-1's (the receiver's) link cut, the copy went on member to member and landed, but the next call to eu-1 went over the closed link's channel (`Channel has been shut down`, the same as c37's `connect ENOENT`), which was not taken as a link drop. Both fixed on `main`, not released (deplo#378): a move whose copy broke on a link goes again in every case, starting the App on its old server first once that server answers; each volume and the Files go on connections opened for that step.
3. **A deleted App leaves nothing anywhere.** The save of what a returning member had left held the stack's lock for the whole save (1.6 GB, paced, about 10 minutes): the delete's teardown waited on it and failed three times at 180 s, and the save landed on eu-1 after the delete, unreported (the leader no longer named the App, so it was never said, so never removed). A teardown that removes an App's data now ends that save at once and forgets the keep; the receiving store drops a save cut short. Live (canary.92): eu-4, holding lab-pb's copy, was power-cut and back, and lab-pb deleted 3 s after its link came up: Deplo finished the delete 29 s later with no teardown left, and nothing of lab-pb (container, volume, copy, backup) was on any member 60 s after it.
4. **Two name servers silent together.** All six such probes in c37 (19:37:25, 20:17:56, 20:28:14, 20:32:09, 21:10:12, 21:59:23) were one tick each, a different pair each time, while every HTTPS probe in the same tick answered, and no zone change was logged (eu-3 was idle at 20:17:56). c38 counted, with a named nftables counter on each member, every query from Deplo's machine and every answer back: over 1 h 52 min eu-1 answered 7140 of 7141, eu-2 6659 of 6660, eu-3 6568 of 6568, eu-4 6559 of 6562 (the few left at agent restarts). Every probe where two or more name servers missed together had either fewer queries reach the members than were sent (lost on the way, on the lab's uplink: it went down whole at 01:06:20 for two minutes) or an `ETIMEOUT` after 30 to 50 ms (an error on Deplo's machine, nothing sent). The name servers were never silent; nothing in them changed.

Released this round: agent v0.5.3-canary.52 (the leader is unchanged at v0.1.0-canary.22), panel v0.8.2-canary.91 and v0.8.2-canary.92, the second because canary.91's moves waited their turn with their App already stopped (ADR-0049, "What cluster eu showed"). **Not fixed**: a replica handed while its App was still empty is whole at once, so data the App writes later reaches it as followed changes the queue does not count (lab-pd's 300 MB went to eu-4 beside a backup into it); Apps passed on through a busy member to another one stay over 2 s (fise and memos through eu-4 up to 6.4 s, 4 to 8% of probes) because the four one-core members were 83 to 97% busy under the lab's prober alone; certificates issued before canary.91 keep RSA-4096 until their renewal (fise's and memos' in January); a restore from a backup kept on another member still goes through Deplo; a dropped link still ends a move on canary.92 (fixed on `main`, deplo#378).

## A rollout costs no lease, copies wait whole, restores go direct (25 Nov 2026)

On canary.92 the rollout to canary.91 took fise down 100 s and memos 53 s (a lease renewal on eu-2 came 5.3 s late), a move whose link dropped failed on either side, a restore from a backup kept on another member went through Deplo, a copy of a replica handed while its App was still empty escaped the queue, and under load every copy read Behind together for about 35 s. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.53 and .54, panel v0.8.2-canary.93; the leader is unchanged at v0.1.0-canary.22):

1. **A rollout never takes an App down.** Why eu-2's renewal came 5.3 s late: eu-2 has one core and ran the leader. Right after its agent's own update, Deplo recreated its proxy for ECDSA. While the proxy was down (about 45 s), every connection the other members passed on to eu-2 for fise and memos dialed the dead proxy again at each look, every half second, and logged it: 3036 refusals in 25 s, and the agent's service took 70 to 88% of the core. The recreation's own `docker` and `docker compose` commands ran in that service's cgroup too, beside the leader, whose every renewal also crosses the agent's network: the leader renewed all four members 2 to 2.4 s apart, then 4.5 and 5.3 s, and eu-2's agent fenced its Apps. Reproduced on a clone made eu's leader, with 20 new visitors a second: the proxy recreated through Deplo (a server certificate) took the agent from 12 to 77% of the core with 1793 refusals in 14 s. What changed (agent):
   - **One refusal holds a second**: a server whose own proxy refuses a passed-on visitor answers "not ready" to every pass and probe for a second, and logs the outage once. On the clone: one line instead of 1793, the agent at its usual share.
   - **Docker and git commands run below the agent**: in `deplocli.slice` (CPU weight 100, Docker's own), cloned straight into it, so a recreation's commands yield to the leases. With only the first fix, the clone's renewals still came 2.1 to 2.4 s apart at the proxy's restart; with both, none was late across a proxy recreation, an agent restart on the leader's server, and both at once.
   - **A renewal's answer never waits for Docker**: which unplaced stacks still run here is what the last look found, the look running beside the answer.
   - **A recreated or stopped proxy drains 3 s**, not Docker's 10 or the 15 of a stop before a certificate store change: Traefik waits out every passed-on stream, and its server refused every new visitor meanwhile (11 s on the clone).
   - **canary.53 was not enough** (its check on the clone, with a backup running: renewals 4 to 8 s late, the clone fenced its Apps for 41 s). Sampling every process the agent started showed the rest: every passed-on visitor ran its own `docker inspect` for the proxy's process while the proxy was gone, up to 59 a second (436 in 95 s). canary.54 looks the proxy up once for every dial, and a look that found none answers every dial for a second; each App's replicas ask once whether it still runs (it was once per member stream every 2 s), and a backup's `docker exec` keeps the cached docker reads. With canary.54 the same check left every renewal on time.
2. **Restore goes direct.** A restore from a backup kept on another member reads it from that member over the cluster's network (`ExpectClusterFetch`, `RestoreRequest.member_fingerprint`), checked against the backup's sha256; Deplo relays it only when no path joins them, before a byte is read. Activity says `Restored X from a backup, server to server` or `, through Deplo`.
3. **The queue counts every copy.** A copy that moves data takes its servers' turn: not whole yet, behind, or taking 8 MB since the last pass (a catch-up, or what an App empty at its first copy writes later). One that held a turn keeps it while it copies; one a backup or a move overtook, or that waits for a busy end, is held whole and idle on its member (`ClusterReplicaEntry.hold`), reads **Queued**, and a failover can still use it. **Why every copy read Behind at once**: a copy is behind once it heard nothing for 30 s, and the page measured that against now from the last time Deplo stored the copy's status; the replication pass runs every 15 s and contacts every member twice in turn, so under load it came every 30 to 40 s and every copy crossed 30 s together (c38: their `appliedAt` advanced in 22 to 32 s steps). A copy is now judged by its age when Deplo read it.
4. **#378 ships**: a move whose copy broke on a link goes again in every case, its App started on its old server first once that server answers, each volume and the Files on connections opened for that step.

## Copies in the order asked, a leader that steps aside, no 404 (25 Nov 2026)

On canary.93 a backup waited 12 minutes behind copies that asked after it, a 300 MB backup ran at 13 KB/s, the leader's own server updating its agent held every renewal 2.4 s, a connection kept open across a move got 404 from the server the App left, a recreated proxy answered 404 for seconds, a deleted App's volume came back empty, and a new App was not reachable by name for 31 s. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.55, panel v0.8.2-canary.94; the leader is unchanged at v0.1.0-canary.22):

1. **First come, first served.** Why lab-r's backup waited: a backup looked every 5 s whether its servers were free, while the replication pass (every 15 s) handed a server whose copy had just ended to the next copy in the same pass, so the backup never saw it free; and of two backups whichever looked first won. Now every copy joins one line the first time it asks, a backup, a new copy and a copy held whole alike (`lib/data/clusters/copy-turns.ts`), and goes only once none of its servers copies and nobody who asked before it waits for one of them. A copy that holds a turn keeps it while it copies. Each queued copy says its place: `Queued: 2nd in line: eu-1 is busy with a copy of web` on the copy, `Waits its turn, 2nd in line: ...` on a backup's run. A move still never waits (its App is down until it copies, c38). What another cluster left in line on a server is dropped: a server is in one cluster.
2. **A copy always moves.** Why 13 KB/s: a copy waited four times its last step whenever any visitor had crossed the agent since its last look (the prober, every second), and whenever the waits of every container summed past a twentieth of the step, the proxy's and the forwarders' included. Measured on eu with only visitors (the prober): the busiest container, fise's database, waited 0.6% of the time for the CPU, every other under 0.3%, none for the disk. Now a copy gives way only while **one** container waits for the CPU or the disk more than **10%** of a step (the threshold; backing off from four to 32 times its step, as before), never for a visitor, and never runs under **2 MB/s** (the floor): a step and its wait together take no longer than its bytes at that rate, so 300 MB takes at most 150 s however busy the Apps are. Live on canary.94: a 304 MB backup from the clone eu-4 to eu-3 took 38.6 s and into eu-2 (fise's and memos's server) 39.0 s, and three 300 MB copies of the same App 25 to 40 s each, every App by name and through every member within 0.3 s throughout. The threshold did its job on eu-2: fise's database waited 24 to 32% of a second at the copies' peak, the copy gave way, and fise answered in 0.1 s.
3. **The leader steps aside before its server updates.** The rollout updates a server that leads a cluster after the other servers, and right before its agent updates hands each cluster it leads to the first in line, one already on the pin first (`handLeadersOff`). The hand-over itself costs no renewal: moving eu's leader through Deplo, every member's renewal across the new epoch came 0.94 to 0.96 s after the one before (eu-2 to the clone eu-4, epoch 94), 0.70 to 0.74 s (95), 0.99 to 1.00 s (96), 0.44 to 0.45 s (97, under 20 new visitors a second) and, in the rollout itself, 0.93 to 0.95 s (98, eu-1 to eu-2, Activity: `The leader of cluster eu now runs on eu-2, next in line, while eu-1 updates its server agent`). No renewal of the rollout came more than 1.07 s after the one before, the leader's server's included.
4. **No 404 for an App that exists.** Every visitor of a domain that answers on every server reaches the App's proxy through the agent of a server that runs it, that server's own visitors too: each proxy passes its own Apps' TLS to its answer forwarder. So the agent can keep both promises. (a) A connection kept open across a move is closed by the old server's agent once the placement no longer puts the App there (`carry`, `watchLocal`), and the client reconnects: live, moving lab-p from eu-3 to eu-1 with one connection kept to eu-3 itself and one through eu-2, each had the one request in flight while the App was stopped time out (the client's own 5 s), then answered 200 on a new connection; no 404, as on the clone. (b) A restarted proxy gets no visitor for `answerSettle` (3 s) after it starts, the time it takes to read its routes: on canary.54 each recreation answered one 404 through every member, about 0.2 s after the proxy was back; on canary.55 none through any member, none in 1780 new visitors during a recreation on the clone (canary.54: 60), and none by name when eu-1's proxy was recreated through Deplo live (fise and memos answered in 0.1 s; lab-p, which ran there alone, waited up to 8 s and answered). Left: a connection to the restarted server itself in the first tenth of a second can still meet Traefik before it read the passthrough routes (one 404 from the server itself, seven `DEPTH_ZERO_SELF_SIGNED_CERT` in the burst).
5. **A deleted App stays deleted.** Every helper container that reads a volume mounts it read-only (a backup's copier and tar, a set-aside, an adopt, a copy's export), and Docker makes a missing named volume for any mount, read-only or not, so a helper started after a delete made the volume again, empty. Which helper did it in c39 was not caught: a backup asked a second before a delete, and a delete followed 10 s later by a leader hand-over off the App's server (as in c39), recreated nothing on any member on canary.93 either. Now a helper never makes a volume it only reads: a missing read-only mount turns the run into `docker volume inspect` of it, which fails, so whatever starts one after a delete fails instead. Live: lab-m, with copies on three members and backups on three, was deleted at 08:49:42; 2 and 10 minutes later no member held anything of it (container, volume, copy, backup, stack files), nor 2 minutes after of the five lab Apps deleted next.
6. **A new App by name.** Two causes, both Deplo's. (a) The zone answered "no such name" with a 30 s negative TTL (its SOA minimum), so a resolver that asked before the App was ready kept that answer 30 s: the prober's own resolver, asking at once, found lab-qc and lab-qd exactly 30 s after its first look. Now 5 s. (b) Adding a domain handed every member its table, then every proxy and every App's certificates, one server after another, and only then put the App's route in place: lab-d answered 404 on every server for 12 s after the panel said ready, its route 15 s after the domain was added. Now the tables go to every member at once, the route follows, and the proxies and certificates after. Live: a new App answered by name 8.4 s after the panel said ready (7.1 s through every member), the resolver that had asked first included. Left: with the route first, the App is recreated a second time some 13 s later, once its certificates are in step (one 502 probe on lab-n3); and the lab's own image, whose process ignores SIGTERM, takes Docker's 10 s to stop at each recreation (14 to 19 s by name).

## One recreate per domain, every visitor through an agent, the whole sweep again (25 Nov 2026)

On canary.94 adding a domain recreated its App twice (one 502 at each), a just-started proxy could still answer 404 for a tenth of a second, `source-machines.test.ts` failed once on main's CI, and a lab script had printed the panel's API token through `ps`. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.56, panel v0.8.2-canary.95; the leader is unchanged at v0.1.0-canary.22):

1. **Adding a domain recreates the App once.** A domain added to a cluster App was routed with no certificate mode (`cert_challenge` null, so HTTP-01), and the zone's next pass set it to `zone` and routed the App again: on canary.94, lab-a's domain gave two recreates 3 s apart, the second the second its mode turned `zone`. The domain is now marked the way the zone's last pass checks its names (`settleCertModes`, from the eligibility that pass found) before its first route, so the pass finds nothing to change. The 502 at each recreate had a second cause, below (3).
2. **No 404 from a starting proxy.** Traefik applies its first configuration once its own `internal` provider is in, and that provider is never throttled, while the file provider (the passthrough routes of every cluster domain) goes through the 2 s throttle on a goroutine and lands a moment later: until then every cluster domain answered 404 there. A throwaway Traefik 3.7.17 on a member, started six times under a burst of new connections: 404 at five starts in six (50 to 100 ms) with the default throttle, none with `--providers.providersthrottleduration=0`, which every proxy that passes cluster domains on now runs with (one restart of each, through the usual answer pass). Live, eu-4's proxy recreated through Deplo with 20 new connections a second straight to it: no 404 and no self-signed certificate in 1580 (canary.94 on the clone: one 404, seven self-signed).
3. **Every visitor of a cluster domain goes through an agent, its App's own server's too.** canary.94 rendered the App's router on `websecure,answer`; on its own server Traefik matches an HTTPS router's `Host` before a TCP passthrough of the same name, so that server's visitors never reached its agent (checked on eu-3: three connections held to lab-b, no new connection to the `answer` entrypoint). That is where the 502 at each recreate of a domain add came from, why a connection kept to the server an App left answered 404 for the 57 s it stayed open (canary.94, lab-c), and why, after a 2-minute hang, the thawed server's stale copy of lab-b answered a visitor before its agent fenced it, then 404 on the same connection. The router is now on `answer` only (an App changes at its next route), and a reroute holds the App's visitors on its server while its containers are replaced (agent canary.56: a ready answer was kept 5 s). Live on canary.95: one recreate per domain added, no 502 or 404 through any member, each recreate holding a visitor about 3 s; a move with connections kept to the old server, another member and the new one: no 404, each lost the one request in flight and answered on a new connection.
4. **No flaky test.** `source-machines.test.ts` counted every dial of the shared `srv_1` through its agent stub, and a deploy test file run before it in the same worker left its image sweep running, which dialed `srv_1` twice through that stub (the two `[cleanup] deploy-time image sweep on srv_1 failed` lines at that moment); reproduced with two simulated leftover dials, the test now counts only its own machine. The agent's `TestVolumeBackup_freezesTheAppWhereTheProxyCannotSeeIt` read its fake `cgroup.freeze` while the agent rewrote it and saw it empty (17 failures in 400 runs, none after skipping a torn read).
5. **No token on a command line.** Every lab `api.sh` and `lab-api.sh` passed `Authorization: Bearer $(cat …)` to curl; the header now goes on curl's stdin (`-H @-`). With a driver running, `ps -eo args` matched the token in no line.
6. **A copy its App outgrew waits for room** (found by the sweep). A copy a server already held whole was never checked for room again: lab-big's copy on eu-3 was whole at 660 MB, the App wrote 1 GB, and the catch-up took eu-3 from 84 to 89% (df), where the agent stopped it at a tenth free, and the next pass started it again, with no warning. A whole copy is now exempt only while its App has not outgrown it by 8 MB, and never once the agent says it stopped it for room; live, the same case was refused with the warning and one Activity line, eu-3 at 84% at most.

Released this round: agent v0.5.3-canary.56 and panel v0.8.2-canary.95, which pins it (ADR-0049, "What cluster eu showed"). The leader is unchanged. **Not fixed**: the leader's own server stopping still stops every member's single-writer Apps for a few seconds, since a member's lease (5 s) runs out before the heir may ask to lead (the 10 s removal time): fise, memos and lab-a, on a member that was fine, were down by name 10 to 15 s; a hung server keeps being named by the zone for its removal time and still accepts TCP, so a client whose resolver or open connection points at it waits (memos 36 s for the prober); fise's failover took 76 s by name, because a pulled image is fetched from its registry on the new server (Deplo copies only the images it builds) and eu-3 no longer held fise's 3.3 GB of them; a member cut from the others but not from Deplo is not a partition on this lab, Deplo's relay joins them (ADR-0047).

## No team swapped, no member fenced, no stale copy, images ahead, no visitor dropped (25 Nov 2026)

On canary.95 a team header the caller could not use was ignored (two lab Apps landed in another team), losing the leader's server fenced every member, a thawed member served an old copy, fise's failover took 76 s for its registry images, and the rollout left every App unanswered 8 to 10 s while its server's proxy restarted. Decided by the owner, and what each turned out to be (agent v0.5.3-canary.57, leader v0.1.0-canary.23, panel v0.8.2-canary.96):

1. **A team the caller cannot use is an error.** `x-deplo-team` (GraphQL, MCP, the migration export) and the team in a session's URL picked another team when they named one the caller could not act in (`identityForTokenRow` fell back to the first team the token reaches, `pickActiveTeam` to the cookie's or the first). Six tests had pinned the fallback.
2. **Losing the leader stops no App on a healthy server.** The member's lease was 5 s and the heir may ask to lead only once its own lease went unrenewed for the removal time (10 s): every member fenced before the heir could renew it. The lease is now **20 s** (`lease.FenceFor`, carried in every renewal); the takeover stays the heir's ask at **10 s** after its last renewal, the next in line 5 s later (ADR-0049, "Times"). The first heir renews about 11 s after the last renewal, the second about 16 s, both inside the lease. A dead member's Apps with data move once its fence is over (20 s + 11 s for its agent to stop them). Agents from canary.11 keep to the fence a renewal gives, so `agentMin` stays.
3. **A thawed server never serves a stale copy.** Each visitor carried to the server's own proxy was checked against the lease when it arrived and then once a second: at the thaw, what a kept connection had queued during the hang reached the old copy before that look. Every read carried to the own proxy now asks the lease first, and leases count on CLOCK_BOOTTIME, which also runs while a machine sleeps (Go's monotonic clock does not). A server back after its lease lapsed starts nothing that moved away and sets its copies aside first, as before.

Every member whose agent says `cluster.failover.images` is now handed the registry images of every failover bundle of its cluster (`HoldFailoverImages`, at each bundle push and every 2 minutes); it pulls what it lacks one image at a time, only while a tenth of its disk stays free with the image counted (its size where another member holds it), and cleanup spares them. An image behind registry credentials is still copied member to member.
5. **A proxy restart drops no visitor.** While a server's proxy is down, an nftables redirect (`deplo_proxy_hold_<n>`, ahead of Docker's) leads its ports 80 and 443 to the agent: a visitor of a cluster App goes through the agent's own answer path, at once to another server that runs it, or here once the proxy is back; any other is handed to the new proxy. No App counts ready here from the proxy's stop until 0.5 s after it is back (a visitor held through another server met the new proxy before it read its routes: 404), what was found ready before the restart stays ready, and the old proxy drains 1 s (3 s before). ## Images from members, visitors kept across an agent restart, a standby proxy (25 Nov 2026)

On canary.97 three things still cost visitors (above): the name servers went silent from Deplo's machine during the rollout, an agent restart reset what reached its server, and an App on one server waited its proxy's whole restart. Decided and done (agent v0.5.3-canary.58):

1. **What silenced the name servers was the lab's link to the internet, not Deplo.** The registry downloads were blamed; the evidence says otherwise. In the 4 silences of the canary.96 rollout every member renewed every second (the leases cross the lab's own network), Proxmox counted 12 to 36 MB in a minute into the members, and the one big download (fise's images on eu-1, 680 MB in a minute) came after them with no silence at all. A 27 MB binary sent at 80 Mbit/s into the lab and 40 MB over SSH silenced nothing. In this round, with no rollout, the same silences came 5 times in an hour (3, 12, 3, 3 and 2 s): during each, eu-3 still reached eu-1 over the lab's network with no loss, Deplo's machine still reached its gateway and a public resolver with no loss, and eu-3 and Deplo's machine lost every packet between them, both ways, while neither sent more than a few hundred KB a second; none came at one of the dozen binary uploads to a clone. The home line drops, by itself, for seconds at a time.
2. **Images go member to member anyway.** A member missing a registry image its cluster holds for failovers asks the other members for it over the cluster's network (`IMAGEGET`, answered only for an image on that member's own failover list and only to a member of its cluster, one send at a time per member), and loads what one sends. Only when no member holds it does a member download it from its registry, and only the cluster's first member (by certificate): the others wait for it, and take it from there, for 10 minutes before they download it themselves. That download reads the registry's blobs itself, at 4 MB/s and giving way to the server's Apps like every copy, each blob checked against its digest, and hands `docker load` the archive; an image pinned by digest, or one the registry describes in a way it cannot read, is pulled by docker as before. A deploy still pulls its own image at full speed.
3. **An agent restart or crash drops no visitor that arrives meanwhile.** The listeners the forwarders hand visitors to live in systemd's file descriptor store (`FileDescriptorStoreMax`, `FileDescriptorStorePreserve=restart`, `NotifyAccess=main`, added to the agent's own drop-in), so after a `kill -9`, a crash or a restart a visitor waits in the socket's queue until the next run takes it; a self-update's exec hands them over directly. Before it exits or execs the agent takes no visitor (another member passing one gets "not ready" and holds it), lets those it carries finish until they go quiet (at most a second), and writes down what it knew: the Apps it found ready and its proxy's process, also every 2 s while Apps are found ready, so a crash leaves it too. The next run takes its listeners back before any docker call, answers on the lease it kept on disk in this boot (a lease no leader can have moved a writer away within; it decides no start and no certificate), and starts from what the run before knew. A visitor already inside the agent at the moment it is killed is still cut: its bytes cross the agent.
4. **A proxy restart makes nobody wait.** Before the proxy stops, a standby copy of it starts beside it (`deplo-traefik-standby`: the proxy's image, command, environment and networks, no port, no alias, a copy of what it writes and of the routes compose copied into it) and counts ready once it answers a domain a running container routes as the proxy does (on the answer entrypoint behind its PROXY header on a cluster server); the front-door hold hands it every visitor at once, a cluster App's own too, on a single server as well, and it ends once the visitors it carries are gone (at most 30 s after the new proxy settled). Only the proxy's own compose service is recreated: recreating the whole file restarted the socket proxy the standby reads its routes through, and it answered 404 for 3 s. A server with no room or no running proxy restarts as before.
5. **A failover's App takes visitors 2 s sooner.** An App counts ready 1 s after its last container started (3 s before) on a proxy whose providers are not throttled, which every cluster server's proxy is since canary.95; any other proxy keeps the 3 s. The lease and its fence stay: see ADR-0049 for where the time goes.
6. **The log says what happened:** "started lab-a again: the lease places it here" is written once the start ran; a renewal that placed the stack elsewhere says nothing of a start (canary.57 wrote "starting lab-c, lab-a again" at a thaw while neither started).

Measured (ADR-0049, "What cluster eu showed"): the rollout left no App unanswered and no name server silent past one sample; a member took a 1.62 GB image from another member over the lab's network; a proxy restart on a member running a lab App alone, and an agent `kill -9`, answered every visitor that arrived meanwhile; a member's Apps with data came back 37.6 s after its power cut. **Not fixed**: a member that asks a busy member downloads from the registry (DeploCloud/deplo-agent#130, not released); a readiness look due during a proxy restart waits for docker, busy recreating the proxy (3.8 s; same PR); visitors in flight inside an agent that is killed are reset with it (27 of 1180 at 20 new a second); the leader's hand-over held renewals 1.49 s; losing the leader's server still takes about 50 s; and a leader moved onto a member back from power cuts led on a placement hours old, which stopped fise for 1 min 51 s and memos for 12 min 49 s (deplo-cluster's takeover and the panel's hand-over, `lib/data/clusters/leader-move.ts`).
