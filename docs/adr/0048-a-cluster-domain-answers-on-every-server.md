# ADR-0048: A cluster domain can answer on every server

**Status**: proposed. Builds on [ADR-0047](0047-a-cluster-shares-a-private-network-over-wireguard.md) (the private network carries the traffic) and amends [ADR-0045](0045-a-cluster-leader-holds-sealed-failover-bundles.md) (the bundle carries the certificate). [ADR-0049](0049-a-cluster-can-answer-for-its-own-dns-zone.md) is the path that removes the hand-written records.

A failover moves an App, and its address must follow it **without Cloudflare being required**. Today only a domain served by a Cloudflare tunnel follows; a generated name follows by being renamed (it is a server's IP); any other domain keeps pointing at the server that stopped. **A domain of a cluster App can be set to answer on every server of the cluster ("Answer on every server"): each server passes its encrypted traffic, untouched, over the private network to the server that runs the App, and DNS names every healthy server.** Cloudflare stays a supported way to follow, not the only one.

## Decision

- **Opt-in per domain, off by default.** Every server then carries some traffic of an App it does not run. Only an HTTPS domain on the default entrypoint can turn it on: an HTTP-only one would put a router of its own on `web` beside the challenge router below.
- **Never for a hostname shared by path.** One team may serve `app.com` and `app.com/api` from two Apps (AGENTS.md). Passthrough by SNI sends a whole hostname to one server and cannot split it by path, and a failover may separate two Apps that run together now, so the switch is refused for any hostname another App serves a path of, and a path cannot be added to a hostname that has it on.
- **The traffic goes through the server agents, never to a mesh address.** The private network connects agents, not containers (ADR-0047), and the proxy never sees an address of it. On server M, which does not run the App, and server X, which does:
  1. M's proxy matches the hostname by SNI on `websecure` with TLS passthrough (a TCP router), and sends a PROXY protocol v2 header first. Traefik takes the TCP `serversTransport` that does it from the file provider only, so it ships in the proxy's own file configs, beside `deplo-cluster-relay.yml`.
  2. The TCP service is a forwarder container M's agent runs on the proxy's `deplo` network, the same kind as a name forwarder: no privilege, read-only, and only the agent's socket mounted.
  3. The forwarder hands the connection to M's agent through that socket, and M's agent opens a stream over the private network to X's agent, naming the domain.
  4. X's agent accepts it only for a domain Deplo says X serves, and connects from the host to the proxy's **internal entrypoint** on its address on `deplo`.
  5. X's proxy reads the visitor's address from the PROXY header, terminates TLS with its own certificate, and routes the request to the App like any other.
- **The internal entrypoint is not published and trusts only the local agent.** It has no port mapping, so nothing outside the server reaches it, and `proxyProtocol.trustedIPs` names only the host side of `deplo` (its gateway), which only processes on the host use: Docker's own proxy for published ports also connects from there, but only to 80 and 443. The public `websecure` never trusts a PROXY header: where that Docker proxy makes every visitor look local, trusting it would let any visitor forge its address. The App's routers for such a domain list both entrypoints.
- **No HTTP/3 for these domains.** The private network carries TCP only, so a browser told `Alt-Svc: h3` would try UDP at a server that forwards none. Deplo's proxy enables no HTTP/3; the internal entrypoint never does, and the switch is refused while a server of the cluster runs a hand-edited proxy that does on `websecure`.
- **Port 80 forwards the domain's certificate checks.** Every other server routes the hostname's `/.well-known/acme-challenge/` path on `web` (an HTTP router on `Host` and that path) to the same forwarder, and X's agent connects it to X's own `web`, where Traefik answers the checks it asked for. So a check from any vantage point reaches the server that asked. It carries no PROXY header: an HTTP router cannot send one, a check needs no visitor address, and `web` is public. Everything else on port 80 still gets the usual redirect to HTTPS.
- **`allowACMEByPass: true` on `web`, and nowhere else.** Without it Traefik answers every challenge path itself at the highest priority and returns 404 for a token it did not ask for. It opens no other surface: only Deplo writes routers (the lint keeps a stack's own Traefik labels to middlewares, `compose-lint/traefik-labels.ts`), a hostname belongs to one team (`assertHostnameNotAnotherTeams`), Deplo puts on `web` no router of its own for an HTTPS host but the challenge one above, and Traefik's own challenge router still answers every token it asked for. `websecure` is unchanged: a TLS-ALPN check already passes through there, as Deplo configures no TLS challenge.
- **The certificate travels with the App.** A failover must not wait for a new certificate (HTTPS errors meanwhile) nor order one each time: Let's Encrypt issues 5 duplicate certificates per name set per week, and an App that moves back and forth would lock its domain out for days. X's agent exports the certificate and key of each such domain from its proxy, Deplo seals them into the App's failover bundle on every renewal, and the server the leader starts the App on installs them before the App answers.
  - **Only for domains with the switch on**, sealed to the leader's key like the App's secret variables, never in a DTO or a log.
  - **Who renews it on the new server: its proxy, once the certificate is in the proxy's ACME store.** On Traefik 3.7.17, with Pebble standing in for Let's Encrypt: a proxy that starts with the certificate in its store orders none while it is valid and renews it itself when its window opens, as one it ordered (an ACME account is not needed: it registers its own); a running proxy does not see a certificate written into its store, and orders a new one; a proxy handed it as a file orders none while it is loaded, but never renews it and goes on serving it once it has expired. So the new server installs the certificate **both ways**: as a file, which answers at once, and in its proxy's store, which the proxy reads the next time it starts; then the file goes, and the proxy renews it. A proxy that has not started again before the certificate's renewal window (30 days before it expires) is restarted by its agent then, once. Each renewal is exported again and sealed into the bundle, so the next failover carries the current certificate.
- **DNS lists every healthy server.** Deplo computes the record set (one A, and one AAAA where there is IPv6, per server that is online and not being emptied) and the domain's **DNS backend** applies it:
  - **a connected provider** (Cloudflare today, `DnsProviderKind`): Deplo writes the set as plain records (`pointAtAddress` writes one today), TTL 60 s, and rewrites it when a server joins, leaves, goes offline or comes back.
  - **manual**: the domain lists every address to add, verification checks that each one is there, and a change of the cluster flags the domain until its records match again.
  - **native**: [ADR-0049](0049-a-cluster-can-answer-for-its-own-dns-zone.md). The backend is a per-domain choice, so it plugs in without changing the rest.

## Considered options

- **DNS-01 where a provider is connected**: rejected. Traefik's DNS challenge needs the provider's API token in the proxy's environment on every server, and a token never leaves the control plane, encrypted (`dns_providers`). The way to reopen it is a DNS server of the cluster's own that answers the challenge, as `acme-dns` does ([ADR-0049](0049-a-cluster-can-answer-for-its-own-dns-zone.md)): no token on any server.
- **TLS-ALPN-01 instead of HTTP-01**: it passes through as well, but means a second certificate resolver on every server; HTTP-01 with the bypass on `web` keeps the one there is.
- **Every server orders its own certificate ahead of time**: rejected. Through passthrough only the App's server can answer a check, and N servers renewing the same names would spend the duplicate limit.
- **A new certificate after each failover**: rejected for the HTTPS gap and the duplicate limit above.
- **The certificate as a file only, renewed by the control plane**: not needed. Nothing could renew it but a new order on the App's server, and the store already does that.
- **Drop the file when the renewal window opens, and let the proxy order a fresh one**: avoids that one restart, but the host answers with the wrong certificate for the seconds an order takes, and it is a new order of a certificate still valid.
- **Terminating TLS on every server**: rejected. The key would sit on every server, and the App's own headers, auth and redirects would run twice.
- **Cloudflare only**: it already follows, and stays; it cannot be the only way.

## Consequences

- **A failover needs no DNS change.** Every server answers for the App, so the domain answers again as soon as the App runs on another server, with Deplo up or not.
- **Deplo down is a degradation, not an outage.** Only taking a stopped server out of DNS waits for Deplo. Until then a visitor's browser that tries the stopped server first falls back to the next address after a few seconds, per visit. With no provider that is permanent until the records are edited, and the manual says so.
- **Failover bundles now carry TLS private keys**, which no member receives at deploy: the one exception to ADR-0045's "exactly what a member already receives". A compromised leader machine also exposes the keys of the domains that answer on every server.
- **Every server's proxy changes once**: the internal entrypoint, `allowACMEByPass` on `web`, and a `serversTransport` file. It rolls out like the agent (`docs/agents/cluster-rollout.md`): the server agent first, its forwarder behind a Hello capability, then each server's proxy, one server at a time. Applying it restarts that proxy: Traefik stops accepting new connections, gives requests in flight up to 10 s (`lifeCycle.graceTimeOut`), and closes every open connection, WebSockets and long downloads included; a visitor reconnects to the new proxy a second or two later, and to another server meanwhile once its domain lists several.
- **A failover may add one restart of the new server's proxy**, up to two months later: only when that proxy has not started again before the travelling certificate's renewal window.
- **Generated names are out of scope.** A generated name is one server's IP by construction; it keeps following by being renamed.
